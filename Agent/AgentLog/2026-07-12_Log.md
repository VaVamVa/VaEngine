## Compact Log #1

### World Space → Scene Scale 전환 — 설계(구현 전, 동의 대기)

**배경**: IBL Stage B + Forward IBL 적용 완료 후, 사용자가 이전부터 저울질하던 "World Space 유지 vs Scene Scale 도입"을 검토. Shading이 늘어날수록 육안 재검증 비용이 커지므로, 향후 Phase 3 Collider/Physics 도입 전에 결정해야 한다는 결론(물리 시뮬레이션은 중력·솔버 epsilon 등이 스케일에 구조적으로 종속되어 "일단 만들고 나중에 스케일 맞추기"가 사실상 불가능 — 조명/노출처럼 슬라이더 재조정으로 때울 수 있는 영역이 아님). `1 unit = 1m`로 컨벤션을 확정하고 설계부터 시작하기로 함.

**조사 결과 — 예상보다 범위가 좁음**: 이 엔진은 이미 거의 전부 `1 unit = 1m`로 동작 중이었음이 확인됨.

| 근거 | 값 | 판정 |
|---|---|---|
| `CubeShape{}` 기본 half-extent | 0.5 (스케일 1.0 → 1m 정육면체) | 이미 미터 기준 |
| `floor->SetScale(20, 0.5, 20)` | 20m×0.5m×20m 바닥 | 그럴듯한 값 |
| Point Light `range` | 15.0f | 그럴듯한 값 |
| ShadowMapRenderer `kExtent`/`kFarZ` | 40 / 100 | 그럴듯한 값 |
| FreeCamera `moveSpeed` | 5.0f (5m/s) | 그럴듯한 값 |
| `kachujin->transform.SetScale(0.01f,...)` (`VaProgramName.cpp:34`) | — | **유일한 예외** — FBX가 cm 단위로 export되어 애플리케이션 코드에서 수동 보정 중 |

즉 "Scene Scale 도입"은 엔진 전체 재작업이 아니라 **`Tools/ImportTool/Converter.cpp`의 단위 보정 로직 부재를 고치는 문제**로 좁혀짐.

**검토했으나 채택하지 않은 방법**:
- `aiProcess_GlobalScale`(Assimp 표준 해법) — `Converter::Convert()`의 `TraverseNode`가 `mesh->mVertices[v]`를 노드 트랜스폼 적용 없이 그대로 읽어(158~180행 확인) 이 옵션이 굽는 루트 노드 트랜스폼이 반영되지 않을 수 있음.
- `aiProcess_PreTransformVertices`(트랜스폼을 정점에 직접 구움) — 스키닝 메시와 비호환(본 계층 구조 파괴) — `ConvertSkinned()`에는 사용 불가.

**제안 설계**: `aiScene::mMetaData`의 `"UnitScaleFactor"`(파일 단위를 cm 기준으로 표기)를 직접 읽어 `scale = unitScaleFactor / 100.0f`(cm→m)를 계산, 정점/본/애니메이션 데이터를 추출하는 지점 4곳에 직접 곱함:

| 위치 | 내용 |
|---|---|
| `Converter.cpp:178-180` (`Convert`) | 정적 메시 정점 위치 |
| `Converter.cpp:486-488` (`ConvertSkinned`) | 스키닝 메시 정점 위치 |
| `Converter.cpp:408` 부근 (`AiMatToFloat16` 결과) | 본 오프셋(inverse-bind) 행렬의 translation 성분 |
| `Converter.cpp:591-593` | 애니메이션 클립 키프레임 translation |

**불확실성 고지**: `UnitScaleFactor` 메타데이터의 정확한 존재 여부·의미는 Assimp 문서 기억에 의존 — 구현 시 값을 디버그 출력해 Kachujin FBX에서 기대값(1.0 근방)이 나오는지 먼저 확인 필요.

**진행 순서**:
1. `Converter.cpp` 4곳 수정
2. VaImportTool 재빌드 + Kachujin FBX 재-임포트 + `_Assets/` 복사(사용자 직접 수행)
3. `VaProgramName.cpp`의 `SetScale(0.01f,...)` 제거
4. 육안 확인 — Kachujin 키(1.7~1.8m 근방), 애니메이션 루트 모션 비율

`CubeShape`/`ShadowMapRenderer`/Light range/Camera speed는 이미 맞는 스케일이라 변경 불필요.

**상태**: **구현 완료.** `Converter.cpp`에 `GetFileUnitScaleToMeters(scene)` 헬퍼 추가 — `aiScene::mMetaData`의 `"UnitScaleFactor"`를 읽어(Assimp FBX importer 소스(`FBXImporter.cpp:176`, 변수명 `size_relative_to_cm`)에서 "파일 1unit = 몇 cm"가 맞음을 직접 확인) `scale = unitScaleFactor / 100.0f` 계산. 4곳에 적용:
- `Convert()`/`TraverseNode()` — 정적 메시 정점 위치(`unitScale` 파라미터로 재귀 전달)
- `ConvertSkinned()` — 스키닝 메시 정점 위치, 본 오프셋 행렬 translation(`AiMatToFloat16` 결과의 `[12][13][14]`), 애니메이션 클립 키프레임 translation

`unitScale` 값을 `std::cout`으로 출력하도록 해 재-임포트 시 실제 FBX에서 기대값(1.0 근방)이 나오는지 육안으로 확인 가능.

**아직 안 한 것(사용자 수행 필요)**:
1. VaImportTool 재빌드
2. Kachujin FBX 재-임포트 + `_Assets/` 복사
3. 재-임포트 확인 후 `VaProgramName.cpp:34`의 `kachujin->transform.SetScale(0.01f,...)` 제거 — **아직 지우지 않음**. 재-임포트 전에 지우면 데이터는 아직 cm 단위인데 보정만 사라져 Kachujin이 100배 커 보이는 회귀가 생기므로, 재-임포트 확인 전까지 의도적으로 남겨둠.

## Compact Log #2 — `.matl` scale= 지원 + Transform Scale/ScaleMultiplier 분리 (구현 완료)

**배경**: Scale 조정 공용 수단을 어디에 둘지 검토하다, 사용자가 "게임플레이 애니메이션(grow/shrink 등)도 곧 필요하다"고 확정 — 애초에 "자동 보정이 안 닿는 예외" 하나만 생각하고 있었으나, 실제로는 **정지 상태의 디자인 크기/임포트 보정**과 **런타임에 애니메이션되는 게임플레이 효과**라는 서로 다른 두 개념이 같은 필드를 두고 충돌할 수 있음이 드러남.

**검토한 대안**: Unreal Engine 레퍼런스 확인 — UE는 `FTransform`에 필드를 두 개 두지 않고, **SceneComponent 부모-자식 계층**으로 두 스케일을 분리한다(월드 스케일 = 부모 월드 스케일 × 자신의 RelativeScale3D). 이 엔진엔 아직 Transform 계층이 없어 완전히 같은 방식은 못 쓰지만, "두 값을 독립적으로 두고 합성한다"는 핵심 아이디어는 계층 없이 필드 두 개로도 동일하게 구현 가능하다고 판단.

**구현 내역**:

| 파일 | 내용 |
|---|---|
| `Engine/Public/Scene/Transform.h` | `scaleMultiplier`(Vector3, 기본값 (1,1,1)) 필드 신설. `SetScaleMultiplier`/`GetScaleMultiplier`(Vector3·float 오버로드) 추가. `GetMatrix()`가 `scale`과 `scaleMultiplier`를 성분별로 곱한 `effectiveScale`로 스케일 행렬 구성 |
| `Engine/Private/Object/WorldModel.cpp` | `ParseTexKey` → `ParseMatlKey`로 개명(텍스처 전용이 아님을 반영). `.matl`의 `scale=` 키 파싱 추가 → `transform.SetScale(std::stof(...))` |
| `Engine/Private/Object/WorldAnimatedModel.cpp` | 동일 패턴 적용(중복 존재하는 기존 구조 그대로 유지) |

**역할 분담**: `scale`(기존 필드) = 디자인 타임 크기 + 임포트 단위 보정(`.matl`의 `scale=`이 여기 해당) / `scaleMultiplier`(신규) = 런타임 게임플레이 효과 전용(grow/shrink/pulse). 두 값은 서로의 존재를 몰라도 충돌 없이 합성됨. 기본값이 항상 (1,1,1)이라 기존 `floor`/`tower`/`cube`의 `SetScale()` 호출부는 전혀 영향받지 않음.

**`.matl` 파서 일반화 관련**: `Refactoring_At260711.md` 항목3(파서 일반화)의 트리거 조건은 "3번째 **텍스처** 슬롯"이었는데 `scale=`은 텍스처가 아니라 트리거 조건에 해당하지 않음 — 지금은 기존 라인 스캔 방식을 그대로 확장.

**상태**: 구현 완료. Kachujin 재-임포트 후 `.matl`에 `scale=`을 넣을 필요는 없어짐(기본값 1.0으로 충분) — 이 메커니즘은 향후 자동 보정이 안 닿는 예외 케이스를 위한 안전망으로 남겨둠.

## Compact Log #3 — WorldObject Local/World Transform Hierarchy (구현 완료)

**배경**: 모자 등 장식을 씌우는 기획을 검토하다, 카메라 붐·정적 오브젝트 부착처럼 부모-자식 관계가 필요한 경우가 곧 생길 것으로 판단. UE의 SceneComponent 계층(Local→World, 부모 스케일×자식 스케일 합성)을 레퍼런스로 검토했으나, **모자처럼 스켈레탈 메시의 특정 본에 붙는 경우는 이 계층으로 풀리지 않는다는 사실을 먼저 확인**(Compact Log #4 참조) — 그래서 이번 Hierarchy는 "본 부착"이 아니라 카메라 붐·정적 오브젝트 부착 등 범용 케이스를 위한 것으로 범위를 좁힘.

**설계**:
- 부모-자식은 **소유권 없음** — Application이 `new`/`SAFE_DELETE`로 WorldObject 수명을 직접 관리하는 기존 관례(`VaProgramName.cpp`)를 그대로 따름. `AttachTo()`/`Detach()`는 포인터 등록만 수행.
- `GetWorldMatrix()`는 매 호출마다 부모 체인을 다시 곱해서 계산 — 캐싱하지 않음. 계층 깊이가 얕아 비용이 무시할 만한 수준이고, 부모가 바뀔 때 자식들의 캐시를 무효화하는 전파 로직을 따로 안 둬도 되어 stale-cache 버그가 구조적으로 발생할 수 없음(성능보다 정확성·단순함 우선).
- 행렬 합성 순서는 `transform.GetMatrix() * parent->GetWorldMatrix()` — 이 엔진의 row-vector 컨벤션(`mul(pos, world)`, `Matrix4x4::Translation`이 `m[3][0..2]`에 위치를 둠)과 일치하도록 로컬을 먼저 적용.
- 소멸자에서 자신을 부모의 children에서 제거하고, 자신의 자식들은 `delete`하지 않고 `parent=nullptr`로만 orphan 처리(소유권이 없으므로).

**구현 내역**:

| 파일 | 내용 |
|---|---|
| `Engine/Public/Object/WorldObject.h` | `AttachTo(WorldObject*)`, `Detach()`, `GetParent()`, `GetWorldMatrix()` 추가. `AddToScene()`이 `Impl_AddToScene` 호출 후 `children`을 재귀 순회하도록 변경(Application이 최상위 오브젝트만 `AddToScene` 호출하면 자식은 자동으로 그려짐) |
| `Engine/Private/Object/WorldObject.cpp` (신규 파일) | 소멸자, `AttachTo`/`Detach`/`GetWorldMatrix` 구현. `DrawGizmo()`도 이 파일로 이동 — 로컬 `transform.Forward()/Up()/Right()` 대신 `GetWorldMatrix()`에서 축을 직접 추출하도록 변경(부모 회전이 반영되지 않던 문제 방지) |
| `Engine/Private/Object/WorldModel.cpp`, `WorldAnimatedModel.cpp` | `Impl_AddToScene`이 `transform.GetMatrix()` 대신 `GetWorldMatrix()` 사용하도록 변경 — 부모가 있으면 실제로 상속되도록 |

**CMake 관련**: `Engine/CMakeLists.txt`가 `file(GLOB_RECURSE ...)`로 소스를 수집하므로 새 `WorldObject.cpp`는 **CMake 재구성(재실행)이 필요** — 단순 재빌드만으로는 새 파일이 인식되지 않음. `cmake --preset windows-directx`를 다시 실행해야 함.

**상태**: 구현 완료, 빌드·육안 검증 대기(CMake 재구성 필요 — 위 참조).

## Compact Log #4 — 모자/장식 부착 메커니즘 조사 (설계 불필요 판정 — 이미 지원됨)

**배경**: 사용자가 캐릭터에 모자 등 장식을 씌울 계획이 있다고 밝혀, WorldObject Hierarchy로 이 문제가 풀리는지 검토.

**핵심 발견**: `Skeleton`(`Engine/Public/Object/Skeleton.h`)은 본의 **정적** bind pose/offset 행렬만 보유. 실제 애니메이션 중 "지금 이 프레임의 머리 본 월드 행렬"은 CPU에서 전혀 계산되지 않고, `BonePaletteCompute`가 GPU 컴퓨트 셰이더에서 계산해 `BonePalette`(StructuredBuffer)에 구운 뒤 스키닝 버텍스 셰이더(`LoadSkinnedBone`)가 바로 읽어 쓴다. 즉 "모자를 본에 붙인다"는 CPU가 갖고 있지 않은 데이터를 참조하는 문제라, 방금 만든 WorldObject Hierarchy(CPU Transform 합성)로는 근본적으로 풀리지 않는다.

**검토한 세 갈래**:
1. GPU→CPU readback — 동기화 스톨 발생, 기피.
2. CPU에서 본 계층 중복 계산 — GPU가 이미 하는 일을 부착 대상 본만 다시 계산.
3. **모자를 본에 100% 가중치로 리깅된 서브메시로 취급** — 실무 표준 방식. 채택.

**갈래 3이 이미 구현되어 있음을 확인**: `WorldAnimatedModel::Initialize()`가 `SkmLoader::Load(skmPath)`의 결과(`result.meshes`, 복수)를 순회하며 **하나의 스켈레톤 위에 여러 SkinnedMesh를 등록**하고 있고(`Engine/Private/Object/WorldAnimatedModel.cpp:49-56`), `Impl_AddToScene()`도 그 서브메시 전부를 **동일한** `transformsMap`/`tweenBuffer`(같은 본 팔레트)로 렌더링한다(`WorldAnimatedModel.cpp:207-219`). 즉 **모자 메시가 머리 본에 100% 가중치로 리깅된 채로 Kachujin과 같은 FBX 파일 안의 별도 메시 오브젝트로 존재하기만 하면, 엔진 코드 변경 없이 그대로 렌더링된다.**

**남는 갭(지금 구현하지 않음)**: 별도로 export된 모자 `.smesh` 파일을 캐릭터의 스켈레톤에 **동적으로 추가**(런타임 착용/탈의)하는 기능은 없음 — 지금은 "모자가 처음부터 캐릭터 FBX 안에 같이 있는" 경우만 지원. 실제 모자 에셋이 없어 본 인덱스 매핑(이름 기반 재매핑 필요 여부 등)을 검증할 방법이 없으므로, 이 갭은 **실제 모자 에셋이 생기는 시점에 설계**하기로 함(추측성 구현 금지).

**상태**: 조사 완료 — 엔진 코드 변경 불필요. 아티스트 워크플로(모자를 캐릭터 FBX에 같은 스켈레톤으로 포함) 확인만 남음. 동적 착탈 기능은 별도 기술 부채로 등록.

## Compact Log #5 — Tower 축소 회귀 진단 + 임포트 사이드카 오버라이드 (구현 완료)

**증상**: Kachujin·Tower를 함께 재-임포트한 뒤 "Tower가 너무 작다" 보고. `Tower.mesh`/`Tower.matl`이 Kachujin 에셋과 동일 시각(21:35)에 재생성된 것을 타임스탬프로 확인 — Kachujin만이 아니라 전체 에셋이 재-임포트되며 Compact Log #1의 cm→m 보정이 Tower FBX에도 적용된 것으로 진단.

**근본 원인**: Tower는 이전(보정 전)에 이미 정상 크기로 보였음 — 즉 원본 정점 좌표 자체가 이미 미터 기준. 그런데 Tower FBX의 `UnitScaleFactor` 메타데이터가 cm를 가리키고 있었다면(정확한 값은 미확인, 재-임포트 시 콘솔 로그로 확인 필요), 메타데이터를 무조건 신뢰하는 로직이 불필요한 100배 축소를 적용한 것.

**상용 엔진 비교**: UE(`Import Uniform Scale` 수동값 + Convert Scene Unit), Unity(Model Import Settings의 `Scale Factor`가 자동 추정되지만 Inspector에서 에셋별로 노출·수정 가능), Godot(Import 독의 `Scale` 오버라이드) — 전부 **자동 감지를 기본값으로 쓰되 에셋별 오버라이드를 항상 열어둔다**. "메타데이터를 무조건 믿고 조용히 적용"하는 엔진은 없음. "FBX 임포트 시 스케일이 이상하게 들어온다"는 UE/Unity 커뮤니티에서도 흔히 보고되는 문제로, 이번 Tower 사례가 특별한 게 아님을 확인.

**설계 결정**: 오버라이드를 **런타임**(`.matl`의 `scale=`)이 아니라 **임포트 시점**(원본 데이터에 cook)에 적용 — 상용 엔진들의 실제 관례와 일치하고, 나중에 Physics 등 메시 원본 크기를 직접 참조하는 시스템이 생겨도 런타임 보정을 신경 쓸 필요가 없어짐. `.matl`의 `scale=`은 원래 설계대로 "FBX 파이프라인 밖의 예외"를 위한 최후 수단으로 남겨두고, FBX 스케일 불일치의 주 해법으로는 쓰지 않음.

**구현 내역** (`Tools/ImportTool/Converter.cpp`):
- `GetFileUnitScaleToMeters(scene, fbxPath)` — FBX 옆에 `{stem}.import.txt` 사이드카 파일이 있으면(`unit_scale_override=<m per file-unit>` 키, `.matl`과 동일한 라인 스캔 파싱) 메타데이터 자동 감지를 건너뛰고 그 값을 최종 배율로 직접 사용. 없으면 기존 `UnitScaleFactor` 자동 감지로 폴백.
- `Convert()`/`ConvertSkinned()` 호출부에 `path` 인자 추가 전달.
- `Tools/ImportTool/Assets/Input/Tower/Tower.import.txt` 신규 생성 — `unit_scale_override=1.0`(자동 감지를 건너뛰고 원본 좌표를 그대로 사용, cm→m 변환 없음).

**사용자 수행 필요**: VaImportTool 재빌드 + Tower 재-임포트(콘솔에 `Unit scale override: 1 (m per file-unit, from Tower.import.txt)` 출력 확인) + `_Assets/` 복사 + 육안 확인. Kachujin 쪽 `unitScale` 값도 재-임포트 로그에서 1.0 근방(=cm→m 보정 정상 작동)인지 함께 확인 권장.

**상태**: 구현 완료, 육안 검증 완료. 재-임포트 시 콘솔에 `Unit scale override` 메시지 출력 확인, Tower 크기 정상화 확인됨 — 진단(메타데이터 자동 감지가 Tower에는 부적절했다는 것)이 맞았음이 실증됨.

**Kachujin 쪽도 확인됨**: Kachujin은 Tower와 같은 배치(21:35) 재-임포트 때 이미 정상으로 확인되어 별도 재-임포트 불필요 — 즉 Kachujin은 메타데이터 자동 감지(오버라이드 없이)가 정확히 작동한 케이스로 최종 확인됨. `VaProgramName.cpp:34`의 주석 처리돼 있던 `kachujin->transform.SetScale(0.01f,...)` 잔여 라인도 완전히 제거(더 이상 필요 없음이 확정됐으므로 죽은 주석으로 남기지 않고 삭제).

**최종 결론**: Kachujin(자동 감지 정확) + Tower(자동 감지 부정확, 오버라이드 필요) 두 사례로 "메타데이터 자동 감지를 기본값으로 쓰되 에셋별 오버라이드를 항상 열어둔다"는 설계가 실제로 유효함이 두 방향 모두에서 실증됨. World Space → Scene Scale 전환 작업 완결.

## Compact Log #6 — SSAO 구현 (`G_Smith IBL k 분리` 항목 재개, 구현 완료)

**배경**: `1 unit = 1m` 확정으로 이전에 SSAO를 미뤘던 이유(반경 파라미터가 world-space 단위에 의존하는데 스케일 미확정)가 해소되어 재개. 반경 `0.5m`로 원칙 있게 시작(이전에는 근거 없이 눈대중으로 정할 수밖에 없었음).

**SSAO로 얻는 효과**

- **문제 상황(SSAO 이전)**: IBL Diffuse/Specular ambient(`EvalAmbientIBL`)는 표면 법선 N 방향에만 의존하는 계산이라, 주변 지오메트리가 빛을 실제로 가리는지는 전혀 반영하지 않는다. IBL 적용 직후 Q&A에서 이미 짚었던 지점("IBL은 shadow/occlusion과 무관") — 그 갭을 메우는 것이 SSAO의 존재 이유.
- **구체적으로 밝아지던 것이 어두워지는 지점**:
  - Kachujin의 팔이 몸통에 붙는 겨드랑이·팔꿈치 안쪽, 손가락 사이, 옷 주름 안쪽처럼 오목하게 맞닿는 부위 — 지금까지는 열린 공간과 똑같은 밝기의 ambient를 받아 형태가 평평해 보였음
  - Tower가 바닥과 맞닿는 기저부, 창틀·처마 안쪽 등 구조물의 오목한 디테일
  - 오브젝트끼리 서로 근접·접촉하는 모든 지점(예: floor와 tower/kachujin의 접지면)
- **결과적 효과**: 위 지점에 자연스러운 contact shadow(접촉 음영)이 생겨 입체감·공간감이 살아남. 특히 이 엔진은 Directional Light 하나 + 약한 IBL ambient 구조라 지금까지 "그림자 안쪽인데도 밝게 뜨는" 현상이 상대적으로 눈에 띄기 쉬운 조명 구성이었음 — SSAO가 그 부분을 가장 직접적으로 보완.
- **한계(과대평가 방지용 고지)**:
  - 직접광(Directional/Point/Spot)에는 적용 안 됨 — 이미 Shadow Map이 담당하는 영역이라 중복 차폐하지 않도록 의도적으로 뺌
  - Forward/Transparent 경로 미적용 — 반투명 `cube` 등은 대상 아님(IBL Stage B와 동일한 범위 제한)
  - Normal Map 수준의 미세 요철까지는 못 잡음 — Depth 버퍼 해상도 기준의 거시적 형태(신체 부위 사이, 구조물 오목한 부분)만 반영, 표면 재질의 잔주름 같은 디테일은 여전히 Normal Mapping의 몫

**설계**: 기존에 정리해뒀던 안(GBufferPass → SSAORawPass → SSAOBlurPass → DeferredLightingPass, Bloom과 동일한 풀스크린 삼각형 PS 체인, world-space 히미스피어 커널 + 노이즈 기반 Gram-Schmidt 회전) 그대로 진행. IBL Stage B 이후 달라진 지점만 반영 — `EvalAmbientIBL()`의 반환값에 `ambient *= ssao;`로 곱하는 형태. 1차 구현은 Deferred(불투명) 경로 전용, ambient(IBL)에만 적용(직접광은 Shadow Map이 이미 담당하므로 중복 차폐하지 않음) — IBL Stage B와 동일한 점진적 확장 패턴.

**사전 조사로 밝혀진 사실 — `PointSampler`(s1) 미배선**: `Sampler.hlsli`에 `SamplerState PointSampler : register(s1);`가 선언은 되어 있었으나, `BindingLayout_DirectX.cpp`의 루트 시그니처 생성 코드가 s0(wrap)+s2(shadow comparison) 정적 샘플러 2개만 등록하고 s1은 등록하지 않아 실제로는 죽어있던 상태였음(사용하는 셰이더도 이전까지 전무). SSAO 노이즈 텍스처 타일링에 point-wrap 샘플러가 필요해 이번에 s1을 실제로 배선.

**구현 내역**:

| 항목 | 내용 |
|---|---|
| `Engine/Private/RHI/DirectX/Pipeline/BindingLayout_DirectX.cpp` | 정적 샘플러 2개→3개로 확장, s1(`D3D12_FILTER_MIN_MAG_MIP_POINT`, wrap) 추가 — 기존 s0/s2는 그대로, 하위 호환 유지 |

**초기값(튜닝 필요 예상)**: `radius=0.5m`, `bias=0.025`, `power=1.0`, 커널 32개 — Scene Scale로 근거는 생겼지만 여전히 육안 검증 후 조정 가능성 있음(IBL 클램프 때와 동일한 성격의 초기값).

## Compact Log #8 — Weighted Blended OIT (구현 완료)

**배경**: 지금의 2-Pass CullMode(Front→Back) 투명 렌더링은 볼록 오브젝트 가정에 기댄 근사라, 비볼록 메시·다중 오브젝트 간 순서·서로 꿰뚫는 지오메트리에서 정렬 오류가 남(구체적 실패 형태와 WBOIT 장단점·굴절/투과색과의 관계·런타임 토글 불가 판단 근거는 `2026-07-12_Q&A.md` Q1~Q3 참조). 런타임 토글은 만들지 않기로 결정(Q3) — 2-Pass를 완전히 대체하는 목표 상태로 바로 구현.

**사전 조사로 밝혀진 사실 — RHI가 렌더타겟별 독립 블렌드를 지원하지 않음**: `PipelineState_DirectX.cpp`가 `blendMode`를 PSO 전체에 단일 적용하고(`IndependentBlendEnable` 항상 FALSE) 있었음. WBOIT는 같은 Pass에서 accum(가산)·revealage(곱셈)를 동시에 다른 블렌드로 써야 해서, 범용 독립 블렌드 시스템 대신 `EBlendMode::OITAccumulate`를 신설해 이 조합 하나만 실용적으로 배선(`EBindingType::Sampler`·s1 샘플러와 동일한 패턴 — 지금 필요한 조합만 하드코딩).

**정합성 확인**: 굴절/투과색(향후 작업)은 셰이딩 단계, WBOIT는 합성 단계라 서로 독립 — 이번 구현이 그 작업을 막지 않음(`2026-07-12_Q&A.md` Q2).

**빌드 중 발견된 부수 이슈**: `ColorBuffer_DirectX::Create()`가 모든 컬러버퍼의 optimized clear value를 항상 (0,0,0,0)으로 고정하고 있어, 매 프레임 (1,1,1,1)로 클리어하는 `oitRevealage`에서 `CLEARRENDERTARGETVIEW_MISMATCHINGCLEARVALUE` 경고 발생(정확성 문제 아님, 느린 clear 경로). `IColorBuffer::Create`/`IRenderDevice::CreateColorBuffer`에 `optimizedClearColor` 선택적 파라미터를 추가하는 1차 수정을 했으나, 사용자가 공유한 디버그 로그(`_Files/Log/출력-디버그.txt`)에서 경고가 프레임마다(571회) 여전히 반복되는 게 확인됨 — `OITAccumPass::Execute`의 실제 클리어 호출이 `clearColor[0]`(R)만 1.0으로 설정하고 G/B/A 3개 성분은 기본값 0으로 남아있어 생성 시점 (1,1,1,1)과 여전히 불일치했던 게 근본 원인(R32_FLOAT라 R만 의미 있는 채널이지만 D3D12 검증 레이어는 4성분 전부를 비교). 클리어 호출도 4성분 모두 1.0으로 맞춰 최종 해결. 그 외 D3D12 경고·예외 메시지는 이번 작업과 무관하거나(버퍼 COMMON 상태 경고) 드라이버 내부 정상 동작(Intel MONZA/IGC 예외)으로 확인 — 상세는 `2026-07-12_Q&A.md` Q4 참조.

**육안 검증 결과**: 겹치는 투명 오브젝트(파랑 박스 + 빨강 박스, Kachujin 근처에 교차 배치)로 테스트. 정면으로 겹치는 각도에서 **보라/라벤더 체커 패턴이 선명하게 나타남**(파랑+빨강의 정상적인 혼합), 패턴이 뭉개지지 않고 선명 유지(2겹뿐이라 WBOIT 근사 오차 최소 조건과 일치), Kachujin의 다리·무기가 박스 밖/뒤로 자연스럽게 보여 depth-test도 정상. 검은 구멍·z-fighting·이음매 없음.

**상태**: 구현 완료, 육안 검증 완료, `CLEARRENDERTARGETVIEW_MISMATCHINGCLEARVALUE` 경고 해소도 재빌드 후 확인 완료. weight function 상수(McGuire 논문 기본값)는 추후 레이어가 늘어나면(4~5겹 이상) 재튜닝 필요할 수 있음 — 지금 2겹 테스트에서는 문제없이 확인됨. OIT 작업 최종 완결.
