## Q1. RenderScene vs SceneRenderer 차이

### RenderScene — 데이터 컨테이너 (CPU 도메인)
> 무엇을 그릴 것인가.

한 프레임에 렌더링할 내용을 기술하는 **순수 데이터 스냅샷**입니다. GPU 리소스를 직접 소유하지 않고 포인터/값만 담습니다.

| 보유 데이터 | 역할 |
|---|---|
| `RenderCommand` 목록 | 메시 포인터, 월드 매트릭스, 텍스처, sortKey |
| `CameraData` | view, proj, eyePos |
| `LightingState` | dirLight, pointLights, spotLights |
| 스카이박스 포인터 | `ITexture*` |

매 프레임 `SubmitRenderState()`에서 게임 로직이 새로 구성하고, 렌더 스레드에 전달합니다.

### SceneRenderer — GPU 리소스 소유자 + 렌더 패스 오케스트레이터 (GPU 도메인)
> 어떻게 그릴 것인가.

GPU 리소스를 직접 소유하면서 여러 서브렌더러를 조율해 RenderGraph에 패스를 등록하는 클래스입니다.

| 역할 | 내용 |
|---|---|
| GPU 리소스 소유 | `IDepthBuffer`, G-Buffer RT 3개, HDR RT, Blit PSO |
| 서브렌더러 조율 | `GBufferRenderer`, `LightingRenderer`, `ForwardRenderer`, `AnimationRenderer` |
| 패스 등록 | `AddPasses(RenderGraph&, FrameOutput&, RenderScene&)` |
| 리소스 상태 추적 | `UpdateResourceStates` — 프레임 간 barrier 상태 보존 |

앱 생애 동안 유지됩니다.

### 핵심 구분

```
RenderScene   → "이번 프레임에 무엇을 그릴 것인가" (명세서, CPU 작성)
SceneRenderer → "어떻게 GPU 커맨드로 변환할 것인가" (공장 + 설비, GPU 영속)
```

`SceneRenderer::AddPasses`에서 `RenderScene`을 인자로 받아 데이터를 읽고,
자신이 소유한 GPU 리소스와 결합해 실제 렌더링 패스를 구성합니다.

### 두 클래스가 만나는 지점

```cpp
// SceneRenderer.cpp
void SceneRenderer::AddPasses(RenderGraph& graph, const FrameOutput& output, const RenderScene& scene)
{
    // scene(RenderScene): "무엇을" 읽음
    // graph, depth, gbufferRenderer 등(SceneRenderer 소유): "어떻게" 결정
    gbufferRenderer.AddPasses(graph, skinnedMeshes);   // RenderScene 데이터 → G-Buffer 패스
    lightingRenderer.AddPasses(graph, gbufferRenderer); // G-Buffer SRV → Compute 패스
    forwardRenderer.AddTransparentPasses(graph, output, depth.get());
}
```

## Q2. AddTransparentPasses 필요성 · IRenderer 존재 이유 · SceneRenderer의 인터페이스 가능성

### 1. ForwardRenderer::AddTransparentPasses는 필요한가

**메서드 자체는 필요하고, ForwardRenderer::AddPasses 내부 호출은 데드코드입니다.**

Deferred 파이프라인에서 호출 경로:

```
SceneRenderer::AddPasses
  └─ forwardRenderer.AddTransparentPasses(graph, output, depth.get())  ← 직접 호출
```

`ForwardRenderer::AddPasses`(IRenderer 인터페이스 구현)는 SceneRenderer에서 호출되지 않습니다.
그 내부에서 `AddTransparentPasses`를 재호출하는 것은 순수 Forward 전용 경로 시절의 잔재입니다.

### 2. IRenderer는 이제 필요 없는가

**현재 아키텍처에서는 실질적으로 쓰이지 않고 있습니다.**

`IRenderer`가 의미를 가지려면 `IRenderer*`로 다형적으로 렌더러를 교체하는 코드가 있어야 합니다.

```cpp
// SceneRenderer.h
class SceneRenderer {
    GBufferRenderer          gbufferRenderer;   // IRenderer 미상속
    DeferredLightingRenderer lightingRenderer;  // IRenderer 미상속
    ForwardRenderer          forwardRenderer;   // IRenderer 상속 중이지만 값(value)으로 소유
    AnimationRenderer        animationRenderer; // IRenderer 미상속
};
```

- SceneRenderer가 ForwardRenderer를 값(value)으로 직접 소유 → `IRenderer*` 다형성 없음
- 다른 서브렌더러 3개는 IRenderer를 상속조차 하지 않음
- `IRenderer` 상속은 Forward only 시절의 유산

ForwardRenderer가 IRenderer를 상속하는 실질적 이유가 현재는 없습니다.

### 3. SceneRenderer가 렌더러 인터페이스 역할을 할 수 있는가

**할 수 있고, 오히려 그쪽이 올바른 방향입니다.**

`IRenderer`가 추상화하려 했던 것(GPU 리소스 초기화 + 패스 등록)을 SceneRenderer가 이미 더 풍부하게 담당하고 있습니다.

```
IRenderer (현재)              SceneRenderer (현재)
──────────────────────        ────────────────────────────────────
Initialize(device, desc)      Initialize(device, w, h)
                              InitializeGBuffer / InitializeSky / ...
AddPasses(graph, out, scene)  AddPasses(graph, out, scene)
                              UpdateResourceStates(graph)
```

만약 Forward / Deferred를 교체 가능하게 만들려면 SceneRenderer를 인터페이스화하는 것이 자연스러운 귀결입니다:

```
ISceneRenderer
  ├─ Initialize(...)
  ├─ AddPasses(RenderGraph&, FrameOutput&, RenderScene&)
  └─ UpdateResourceStates(const RenderGraph&)

SceneRenderer         : ISceneRenderer   ← Deferred 구현
ForwardSceneRenderer  : ISceneRenderer   ← Forward only (필요 시)
```

현재 당장 리팩터링할 이유는 없지만, 향후 Forward/Deferred 알고리즘을 교체 가능하게 만들고 싶을 때 이 방향으로 수렴합니다.

> **주의**: Vulkan 백엔드 분리는 이와 무관합니다. 두 축은 독립적입니다.
>
> ```
> 알고리즘 축:  ForwardSceneRenderer | SceneRenderer(Deferred)
> API 축:       DX12RenderDevice     | VulkanRenderDevice
> ```
>
> Vulkan 백엔드는 RHI 계층(`IRenderDevice`, `ICommandList`)에서 처리됩니다.
> SceneRenderer는 RHI 인터페이스만 사용하므로 백엔드가 DX12든 Vulkan이든 SceneRenderer 코드는 바뀌지 않아야 합니다. 그것이 RHI 추상화의 목적입니다.

## Q3. 종합: IRenderer는 지금도 필요한가

**필요 없습니다.**

Q1~Q2와 Vulkan 백엔드 논의를 종합한 근거 세 가지:

**① 다형성이 없다**
SceneRenderer가 ForwardRenderer를 `IRenderer*`가 아니라 값(value)으로 직접 소유합니다.
인터페이스를 통한 교체가 불가능한 구조이므로, 추상 클래스로서의 역할을 이미 못 하고 있습니다.

**② 알고리즘 교체 단위가 아니다**
Forward/Deferred 교체가 필요한 시점이 오면, 교체 단위는 SceneRenderer 전체입니다.
서브렌더러(ForwardRenderer) 수준에서 교체하는 것이 아니므로,
`ISceneRenderer`가 의미 있지 IRenderer는 의미가 없습니다.

**③ 백엔드 분리와도 무관하다**
Vulkan 백엔드는 RHI 계층(`IRenderDevice`)에서 처리됩니다.
서브렌더러 인터페이스인 IRenderer는 이 문제와 관계가 없습니다.

### 생겨난 이유와 소멸 시점

IRenderer는 "ForwardRenderer 하나를 다형적으로 쓰려 했던 Forward only 시절의 설계"였습니다.
Deferred로 전환하면서 SceneRenderer가 오케스트레이터 역할을 가져간 순간 용도가 사라졌고,
현재는 ForwardRenderer에 상속 표시만 남아 있는 상태입니다.

남겨두면 새 서브렌더러를 만들 때 "IRenderer를 상속해야 하나?"라는 혼란을 줄 수 있으므로,
제거하는 것이 더 명확합니다.

## Q4. FrameOutput을 RenderGraph가 자체 처리할 수 있는가

**기술적으로 가능하고 합리적인 근거도 있습니다.**

RenderGraph는 이미 per-frame 객체이고, `ImportResource(backBuffer, ...)`로 backBuffer를 알고 있습니다.
FrameOutput을 내부에 저장하면 모든 AddXxxPasses 메서드의 `const FrameOutput&` 파라미터를 제거할 수 있습니다.

단, FrameOutput에는 개념적으로 다른 두 가지가 섞여 있습니다:

| 필드 | 성격 | RenderGraph에 적합한가 |
|---|---|---|
| `backBuffer`, `backBufferView` | 리소스 식별 — ImportResource로 이미 관리 중 | ✅ |
| `width`, `height` | 프레임 전역 설정 | ✅ |
| `clearColor` | 패스별 렌더링 결정 | ⚠️ 어색함 |

`clearColor`는 패스마다 다를 수 있는 렌더링 의사결정입니다.
또한 shadow map처럼 backBuffer가 아닌 대상으로 렌더링하는 패스가 생기면 "the FrameOutput"이라는 개념이 흔들립니다.

**결론:** 당장 바꿀 이유는 없지만, 렌더 타겟이 다양해지는 시점에 정리하는 방향이 맞습니다.

## Q5. FrameOutput 전용 파일 vs 통합 헤더 vs 기존 파일

### 전용 파일(FrameOutput.h)이 나쁜 패턴은 아닙니다

여러 레이어에서 동시에 참조되는 타입이라면 전용 파일이 include 의존성 측면에서 오히려 깔끔합니다.

### 통합 헤더(RenderTypes.h)로 확장하려면

의미 있으려면 "집이 없는" 렌더링 원시 타입들이 실제로 존재해야 합니다.
현재 코드베이스에서 보면 `ShaderDesc`(IShader.h), `PassResourceDecl`(IRenderPass.h), `ELoadAction`(Common_RHI.h) 등은 이미 제자리가 있습니다.
확장한다면 파일 이름도 `RenderTypes.h` 또는 `RenderCommon.h`로 바꾸는 것이 맞습니다.

### 기존 파일에 둔다면 → RenderGraph.h

FrameOutput과 `RenderGraph&`는 모든 `AddPasses` 시그니처에서 항상 쌍으로 등장합니다.
`RenderGraph.h`를 include하면 패스 등록에 필요한 것들이 갖춰지는데, FrameOutput은 정확히 그 "패스 등록 시 필요한 것" 중 하나입니다.

`Common_RHI.h`는 제외: `EResourceState`, `EPixelFormat` 같은 순수 GPU API 원시 타입의 자리이고, FrameOutput은 한 단계 위의 렌더러 개념이라 계층이 맞지 않습니다.

→ **FrameOutput을 RenderGraph.h로 이동하여 정리.**

## Q6. FrameOutput을 파라미터로 받아야만 하는가

**받지 않아도 됩니다.** RenderGraph가 실제로 보유하면 파라미터가 사라집니다.

FrameOutput은 `Execute::OnRender`에서 한 번 생성된 뒤 아무도 바꾸지 않고 전달만 됩니다.
이는 "프레임 전체에서 고정인 값"을 의미하고, RenderGraph의 프레임 컨텍스트와 같은 생애주기입니다.

RenderGraph가 보유하면:
```cpp
// Execute::OnRender
renderGraph.Reset(backBuffer, backBufferView, clearColor, 1280, 720);
sceneRenderer.AddPasses(renderGraph, scene);  // FrameOutput 파라미터 사라짐

// 패스 구조체 — OnCompile에서 그래프로부터 꺼냄
void OnCompile(RenderGraph& graph) override {
    backBufferView = graph.GetBackBufferView();
    width          = graph.GetWidth();
    height         = graph.GetHeight();
}
```

AddXxxPasses 시그니처 전체가 단순해지고, RenderGraphArguments.h 같은 별도 파일도 불필요합니다.

## Q7. FrameOutput을 RenderScene에 두는 게 적절한가

**적절하지 않습니다.**

RenderScene은 Application 코드가 `SubmitRenderState(RenderScene*)`를 통해 채웁니다.
`backBuffer`와 `backBufferView`는 스왑체인에서 오는 GPU 리소스인데,
Application이 RenderScene을 채울 때 스왑체인 백버퍼를 알 수 없고 알아서도 안 됩니다.

```
RenderScene   → "무엇을 그릴 것인가" (CPU, Application이 작성)
FrameOutput   → "어디에 출력할 것인가" (GPU 도메인, Engine이 처리)
```

FrameOutput은 GPU 도메인에 속하므로 RenderGraph가 올바른 위치입니다.

## Q8. RenderGraph와 SceneRenderer의 관계 · 중복 여부

### 역할 분리

```
RenderGraph    → 메커니즘 : "GPU 커맨드를 올바른 순서로, 올바른 배리어와 함께 실행"
SceneRenderer  → 정책     : "어떤 패스가 있고, 어떤 리소스를 소유하는가"
```

RenderGraph는 SceneRenderer를 모릅니다. SceneRenderer가 RenderGraph를 사용합니다. 계층이 명확합니다.

### 중복처럼 보이는 지점 — 리소스 상태 추적

```cpp
// RenderGraph 내부
unordered_map<IRHIResource*, EResourceState> resourceStates;  // 프레임 내 추적

// SceneRenderer 내부
EResourceState rt0State, rt1State, rt2State, hdrState, depthState;  // 프레임 간 추적
```

같은 리소스의 상태를 두 곳이 들고 있지만 **타임스케일이 다릅니다**:

```
프레임 시작 → SceneRenderer::ImportResource(rt0, rt0State)  ← SceneRenderer가 기억한 상태 주입
               RenderGraph가 내부 추적 시작
프레임 종료 → SceneRenderer::UpdateResourceStates(graph)    ← RenderGraph 최종 상태 회수
               다음 프레임을 위해 SceneRenderer가 보관
```

RenderGraph는 `Reset()`으로 매 프레임 초기화되므로 상태를 기억하지 못합니다.
SceneRenderer가 프레임 경계에서 상태를 보관하는 다리 역할을 합니다.
DX12처럼 리소스 상태를 명시적으로 관리해야 하는 API에서는 피하기 어려운 구조입니다.

### 결론

중복이 아니라 **타임스케일 차이에 의한 역할 분리**입니다.
`UpdateResourceStates`라는 프레임 경계 동기화 패턴이 두 클래스를 연결하기 때문에 혼란스럽게 느껴지지만, 구조적으로 필연적인 분리입니다.
