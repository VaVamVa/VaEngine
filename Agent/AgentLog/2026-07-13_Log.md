## Compact Log #1

### CSM (Cascaded Shadow Map) — 설계 + 구현 완료

**배경**: `2026-07-13_Q&A.md`에서 진행된 사전 논의를 그대로 이어받아 구현. 핵심 결정 사항:

- **Texture2DArray Depth 채택**(Atlas 아님) — Q1 결론. Atlas는 PCF 커널이 캐스케이드 경계를 넘어 인접 캐스케이드 텍셀을 섞는 bleeding 위험을 구조에 내장하는 반면, Texture2DArray는 배열 슬라이스가 물리적으로 분리돼 있어 이 문제가 원천 차단됨. "목표 상태로 바로 구현" 원칙이 엔진을 만드는 현재의 우리가 아니라 향후 이 엔진을 쓰는 대상을 향한 것이라는 사용자 확인에 따라, 착수 난이도보다 구조적 정합성을 우선.
- **Smooth Blend 포함, Dither 제외** — Q4 결론. Dither는 TAA(temporal accumulation)가 있어야 자연스러운데 이 엔진엔 TAA가 없어 제외. Smooth blend는 캐스케이드 선택 로직에 자연스럽게 얹히는 셰이더 로컬 확장이라 기술부채로 미루지 않고 포함.
- **GS/HS 도입 안 함** — Q5 결론. 드로우콜 감소(캐스케이드 인스턴싱)의 폴백일 뿐이고, 이 엔진 타겟 하드웨어는 VS 단 `SV_ViewportArrayIndex`/`SV_RenderTargetArrayIndex` export를 GS 없이 지원할 가능성이 높음. GS 자체가 성능 안티패턴이고 TBDR(Android/Vulkan)에서 더 불리해 멀티플랫폼 방향과도 배치.
- **드로우콜 4배·캐스케이드별 컬링 없음은 기술부채로 유지** — Q3 결론. Atlas/Array 선택과 무관한 별개 문제라 이번 범위에 포함하지 않음.
- **mip level과는 무관한 별개 메커니즘** — Q6 결론. IBL의 mip level(`ITextureUAV`, 텍스처 샘플링 LOD)과 CSM(`IDepthBuffer`, 셰도우 렌더링 LOD)은 적용 방향이 반대인 별개 기법이라, IBL에서 얻은 RHI 역량이 CSM으로 자동 이전되지 않음 — 이번 작업에서 `IDepthBuffer` 쪽에 배열 지원을 처음부터 새로 만듦.

### 설계 — 인터페이스/데이터 흐름

**RHI 계층**
- `IDepthBuffer::GetView(uint32_t slice=0)`/`GetReadOnlyView(uint32_t slice=0)` — 슬라이스 인자 추가(기본값 0으로 기존 호출부 전부 무변경 유지).
- `DepthBuffer_DirectX::Create(..., uint32_t arraySize=1)` — `arraySize>1`일 때만 DSV/readOnly DSV를 N슬롯(`TEXTURE2DARRAY`+`FirstArraySlice`)으로, SRV는 배열 전체를 커버하는 1개(`TEXTURE2DARRAY`)로 생성. `arraySize==1` 경로는 완전히 그대로 유지해 회귀 위험 차단.
- `IRenderDevice::CreateDepthBuffer(..., uint32_t arraySize=1)` — 팩토리 시그니처 확장, DX12 구현체 패스스루.

**RenderGraph 계층**
- `TransientDepthDesc.arraySize`(기본값 1) 추가. `DeclareTransientDepth`의 캐시 비교 로직에 조건 추가(§0-3 alias 방지 원칙 유지), `Compile()`의 리소스 생성 호출에 전달.

**카메라 계층 (CSM에 필요해 함께 확장)**
- `BaseCamera`에 `GetNearZ/GetFarZ/GetFovY/GetAspect` + `SetNearZ/SetFarZ/SetFovY/SetAspect`(값 변경 시 `RebuildProj()` 자동 호출) 추가 — 이전엔 `nearZ`/`farZ`가 protected 멤버로만 존재해 외부에서 읽을 방법이 없었음. Debug/GUI에서 런타임 조정 가능하도록 사용자 요청으로 공개.
- `RenderScene::CameraData`에 `nearZ` 필드 추가, `SetCamera()` 시그니처에 `nearZ` 파라미터 추가.
- **부수 발견 버그**: `CameraManager::SubmitRenderState`가 `scene->SetCamera(view, proj, position)`만 호출해 `farZ`를 아예 넘기지 않고 있었음 — `CameraData::farZ` 기본값(1000.0f)이 그대로 쓰여, `FreeCamera` 생성 시 실제 far(`CameraManager.cpp:36`, 100.0f)와 불일치. CSM의 split distance 계산이 정확한 camera far를 요구해 이번에 nearZ와 함께 farZ도 명시적으로 전달하도록 고쳐 이 불일치를 함께 해소.

**ShadowMapRenderer 계층**
- `kCascadeCount = 4`(compile-time 상수). `lightViewProj`(단일 `Matrix4x4`) → `std::array<Matrix4x4, 4>`, `splitDistances`(신규) → `std::array<float, 3>`.
- **Split 계산**: PSSM(Practical Split Scheme) — `logSplit = near*(far/near)^(i/N)`, `uniformSplit = near+(far-near)*i/N`, `split = lerp(uniform, log, splitLambda)`.
- **캐스케이드별 투영 계산**: `Inverse(camera.view*camera.proj)`로 카메라 프러스텀의 근/원 평면 코너 4+4개를 월드 스페이스로 언프로젝션 → 캐스케이드 구간의 split 비율로 근/원 코너를 선형 보간(뷰 스페이스에서 프러스텀 옆면이 직선이므로 정확) → 8코너의 bounding sphere → `LookAtLH`+`OrthographicLH`로 광원 view*proj 계산.
- `AddPasses`가 `ShadowMapPass`를 캐스케이드 수만큼(4번) 등록 — Bloom/OIT와 동일한 "한 기능 = Pass 구조체 여러 번 등록" 컨벤션.
- `RenderShadowMap(cmdList, scene, cascadeIndex)` — `lightViewProj[cascadeIndex]` 업로드 후 기존 draw 루프 재사용.
- `SetSplitLambda/GetSplitLambda`, `SetBlendWidth/GetBlendWidth` — Debug/GUI 튜닝용 Setter/Getter(사용자 요청).

**DeferredLighting.hlsl / DeferredLightingRenderer**
- `CB_ShadowLightVP`: `viewProj[4][16]` + `splitDistances[4]`(3개 경계+패딩 1개) + `texelSize` + `blendWidth`로 확장. 루트 슬롯 수 변화 없음(root7/8 그대로, CB 크기만 커짐).
- `gShadowMap`: `Texture2D<float>` → `Texture2DArray<float>`(같은 t4 슬롯).
- `CalcShadowFactor`를 `SelectCascade`(카메라 거리로 캐스케이드 선택, `distance(worldPos, EyePos)` 근사) + `SampleCascade`(기존 3×3 PCF에 `float3(uv, cascadeIndex)`) + 경계 근방 smooth blend(다음 캐스케이드와 lerp)로 재작성.

**SceneRenderer 연결부**
- `DeclareTransientDepth({shadowRes, shadowRes, D24_UNORM_S8_UINT, ShadowMapRenderer::kCascadeCount})`.
- `lightingRenderer.AddPasses(...)`에 `GetLightViewProj()`/`GetSplitDistances()`/`GetBlendWidth()` 전달.

## Compact Log #3

### CSM 그림자 소실/유령 그림자 버그 수정 — 완료

**증상(사용자 보고, `ScreenShot/CSM_Bug.png`)**: World Object(Tower/Cube)의 실제 그림자가 사라지고, 아무 오브젝트도 없는 자리에 그림자가 생김. 캐스케이드 색상 오버레이(Compact Log #2)는 정상 표시 — 즉 캐스케이드 **선택**은 맞는데 캐스케이드 **박스 안의 그림자 판정**이 틀어진 상태.

**근본 원인**: `ShadowMapRenderer::ComputeCascades`(C++)는 카메라의 **뷰 스페이스 깊이**(forward축 기준 거리, `camNear`/`camFar` 기반 PSSM split)로 캐스케이드 박스를 분할·피팅했는데, `DeferredLighting.hlsl`의 `SelectCascade`는 `distance(worldPos, EyePos)` **유클리드 거리**로 캐스케이드를 골랐음 — 두 기준이 달랐다. 카메라 축 정면에서는 두 값이 거의 같아 오차가 눈에 안 띄지만, 화면 가장자리나 이번 스크린샷처럼 카메라가 크게 아래를 내려다볼 때(바닥이 화면에 비스듬히 넓게 걸림)는 유클리드 거리가 실제 깊이보다 크게 벌어져 픽셀이 엉뚱한 캐스케이드에 배정된다. 그 결과:
- 실제 캐스터가 있는 자리가 "박스를 만들 때 쓴 깊이"와 다른(대개 더 먼) 캐스케이드로 잘못 배정 → 그 캐스케이드의 UV 범위를 벗어나 `SampleCascade`가 1.0(완전히 밝음)을 반환 → 그림자 소실.
- 반대로 엉뚱한 자리가 다른 캐스케이드의 무관한 깊이 데이터와 우연히 맞아떨어져 잘못된 occlusion 판정 → 유령 그림자.

CSM 설계 시점에 "카메라 forward 벡터를 CB에 새로 추가하지 않아도 되는 실용적 선택 — 광각 FOV가 아니면 오차 미미"라고 판단했던 근사가, 실제로는 오블리크 각도에서 무시할 수 없는 오차였음이 육안 검증으로 드러남.

**수정**: 셰이더가 카메라 forward축 기준 뷰 스페이스 깊이를 직접 계산하도록 `CameraForward`를 `CB_DeferredCamera`에 추가.

| 파일 | 내용 |
|---|---|
| `Engine/_Shaders/DirectX/DeferredLighting.hlsl` | `CB_DeferredCamera`에 `float3 CameraForward` 추가. `camDist = distance(worldPos, EyePos)` → `camDist = dot(worldPos - EyePos, CameraForward)`로 교체 |
| `Engine/Private/Render/DeferredLightingRenderer.cpp` | C++ `CB_DeferredCamera`에 `cameraForward[3]` 추가. `cam.view.m[0][2]/[1][2]/[2][2]`(=`BaseCamera::RebuildView()`가 `LookAtLH`로 채우는 zAxis 성분)에서 월드 스페이스 forward를 직접 추출해 업로드 — 카메라 쪽에 별도 forward 접근자를 새로 만들지 않고 이미 존재하는 view 행렬에서 뽑아씀 |

**정합성 확인**: `ShadowMapRenderer::ComputeCascades`의 split 계산·프러스텀 코너 보간은 원래부터 `camNear`/`camFar`(뷰 스페이스 깊이) 기준이라 수정 불필요 — 캐스케이드를 **고르는** 쪽(셰이더)만 같은 기준으로 맞추면 정합성이 회복됨.

**재검증 결과(사용자 보고, 여전히 동일)**: `CameraForward` 수정 후에도 "이상한 곳에 박스 그림자, 원래 있던 WO는 그림자 없음" 증상 재현(`ScreenShot/CSM_Bug2.png`). D3D12 디버그 로그(`출력-디버그2.txt`) 확인 결과 배열 DSV/SRV 관련 경고·에러 없음 — RHI 레벨 문제 아님.

**이분법 진단**: `DeferredLighting.hlsl`에 `cascade=0` 강제 + blend `#if 0` 비활성화하는 임시 코드를 넣어 "캐스케이드 1개만 쓰는 경우에도 재현되는지" 테스트(`ScreenShot/CSM_Bug3-1.png`, `CSM_Bug3-2.png`). 문제의 도형이 그대로 재현됨.

**원인 재규명 — CSM과 무관한 착시였음**: `VaProgramName.cpp:59-65`의 `transparent_cube1`/`transparent_cube2`(Kachujin 근처 (-5,1,-2)/(-5,1,-1) 배치, 매 프레임 반대 방향으로 계속 회전, 반투명 blend)가 원인. `ShadowMapRenderer::RenderShadowMap`이 translucent 커맨드를 캐스터에서 제외하므로(`sortKey`의 translucent 비트 체크) 이 큐브들은 애초에 그림자 시스템과 무관 — 그래서 `cascade=0` 진단으로도 사라지지 않았던 것. 회전하는 정육면체가 옆면이 카메라와 거의 나란해지는 각도에서 얇은 카드처럼 보이고, 반투명이라 흐릿하게 보여 "박스 그림자"로 오인됨. 사용자 확인 대기 — 확인되면 이 진단 코드(cascade=0, `#if 0`)는 이미 되돌려놓음, 별도 조치 불필요.

**정정(사용자 반박)**: transparent_cube 가설 기각됨 — 사용자가 "회전하는 그림자였으면 처음부터 그렇게 말했을 것"이라고 명확히 반박, 재현된 도형도 회전 없이 정적인 정사각형 그림자 2개("네모 그림자 2개")로 재확인. transparent_cube1/2는 매 프레임 계속 회전하므로 정적인 형태와 모순 — 가설 철회.

**진단 방향 전환 — 스크린샷 대신 실측값 직접 출력**: 화면 해석에 의존한 반복적 오판을 피하기 위해, `ShadowMapRenderer::ComputeCascades`가 실제로 계산한 값(캐스케이드별 split 범위·중심·반경, camNear/Far, lightDir)을 `VA_DRAW_PANEL`(이미 Engine 코드에서 쓰이는 HUD 디버그 패널, `RenderGraph.cpp:145` 참조)로 화면에 직접 출력하도록 `ShadowMapRenderer.cpp`에 임시 진단 코드 추가(키 20~24). 재빌드 후 스크린샷 한 장으로 4개 캐스케이드의 실제 수치(반경이 비정상적으로 크거나 작은지, 중심이 카메라와 무관하게 원점에 고정돼 있는지 등)를 직접 확인 가능 — 원인 확인 후 제거할 것.

**HUD 실측값 확인(`ScreenShot/CSM_Bug4.png`, `출력-디버그3.txt`)**: 4개 캐스케이드의 split 범위·중심·반경이 전부 합리적인 값(반경 0/NaN 없음, 원거리로 갈수록 점진적으로 커짐, 카메라 위치와 기하학적으로 정합)으로 확인됨 — `ComputeCascades`의 bounding-sphere 수학 자체는 정상. 문제는 "박스 계산"이 아니라 "그 박스로 실제로 무엇을 그렸는가" 쪽으로 좁혀짐.

**진짜 원인 발견 — 캐스케이드 간 업로드 버퍼 재사용 레이스**: `IBuffer::Upload()`(`IBuffer.h:17-22`)는 `Map()→memcpy→Unmap()`을 즉시 수행하는 CPU-side write. `ShadowMapRenderer`가 캐스케이드 4개 전부에 대해 **단일 `viewProjBuffer`**를 재사용하고 있었음 — `RenderShadowMap()`이 캐스케이드 0→1→2→3 순서로 같은 버퍼에 `Upload()`를 4번 호출. D3D12 커맨드 리스트는 CPU가 전부 기록한 뒤 GPU가 나중에 한꺼번에 실행하므로, GPU가 실제로 각 드로우를 처리할 시점엔 이미 버퍼에 **마지막에 업로드된 값(캐스케이드 3의 행렬)만** 남아있어, 4개 슬라이스 전부가 캐스케이드 3의(가장 크고 먼) 투영으로 그려지고 있었음. 캐스케이드 0을 강제해도 재현된 이유가 바로 이것 — 버그가 **선택/샘플링**이 아니라 **생성(write)** 쪽에 있었기 때문. D3D12 검증 레이어가 이 문제를 잡지 못한 이유도 명확 — 리소스 상태/타입 오용이 아니라 애플리케이션 책임의 콘텐츠 레이스라 검증 대상이 아님.

**수정**: `ShadowMapRenderer`의 `viewProjBuffer`(단일) → `viewProjBuffers`(캐스케이드별 독립 배열, `std::array<unique_ptr<IBuffer>, kCascadeCount>`)로 교체. `Initialize()`에서 4개 생성, `RenderShadowMap(cascadeIndex)`가 `viewProjBuffers[cascadeIndex]`만 업로드·바인딩. `instanceBuffer`/`skinnedInstanceBuffer`는 캐스케이드와 무관하게 매번 동일한 월드 행렬을 재업로드하므로(같은 내용 덮어쓰기) 재사용해도 안전 — 손대지 않음.

**최종 확인(`ScreenShot/CSM_Bug_Sol.png`)**: Kachujin의 그림자가 실제 자세(웅크린 포즈)와 일치하는 사람 실루엣으로 정상 출력됨 — "박스 그림자"·"WO 그림자 소실" 둘 다 해소 확인. 디버그 패널이 보여준 값은 `ComputeCascades`(CPU)의 계산 결과였을 뿐, 버그는 그 값을 GPU가 실제로 읽을 때(업로드 버퍼 레이스)의 별개 경로에 있었다는 점도 사용자 질문으로 재확인.

**상태**: 근본 원인 수정 완료, 육안 검증 완료. HUD 진단 패널(`VA_DRAW_PANEL` 키 20~24)은 Compact Log #4에서 캐스케이드 활성치 작업과 함께 정리(제거).

### 캐스케이드 7~8에서 그림자 찢김(tearing) 버그 — 원인 확인 + 수정

**증상(사용자 보고, `ScreenShot/CSM_Bug 5-(1~3).png`)**: 활성 캐스케이드를 7·8로 올리면 그림자가 두 개의 정사각형 경계 영역 안에서만 나타나고, 그 사이에는 빈 영역(그림자 없음)이 생김. 캐스케이드 수를 늘릴수록 두 정사각형이 카메라에 가까워지며 좁아지고, 줄일수록 멀어지며 넓어지고 흐려짐. 4캐스케이드에서는 정상(Compact Log #3~4에서 검증 완료).

**원인**: `gSplitDistances`를 `float4[MAX_CASCADE_COUNT/4]`(= `float4[2]`)로 선언하고 `GetSplitDistance(i) = gSplitDistances[i/4][i%4]`로 접근하고 있었음 — **배열 인덱스(`i/4`)와 벡터 컴포넌트 인덱스(`i%4`)를 둘 다 런타임 값으로 계산하는 이중 동적 인덱싱**. 캐스케이드가 5개 이하일 때는 필요한 인덱스(0~3)가 전부 `gSplitDistances[0]`(첫 번째 float4) 안에서 끝나 문제가 안 드러나지만, 6개부터는 인덱스 4 이상이 필요해져 `gSplitDistances[1]`(두 번째 원소)을 처음 건드리게 됨 — 이 지점부터 컴파일러가 이중 동적 인덱싱을 안정적으로 처리하지 못해 잘못된 값을 읽은 것으로 판단. "캐스케이드를 늘릴수록 깨지는 영역이 커진다"는 증상이 "인덱스가 커질수록 두 번째 float4 원소에 의존하는 캐스케이드 비중이 늘어난다"는 원인과 정확히 일치.

**수정**: `gSplitDistances`를 `float4[2]` → 평범한 스칼라 배열 `float[MAX_CASCADE_COUNT-1]`(단일 동적 인덱싱만 사용)로 교체. HLSL cbuffer 규칙상 스칼라 배열은 원소마다 16바이트(float4 슬롯)로 패딩되므로(112바이트, 기존 32바이트보다 커짐 — 미미한 비용), C++ `CB_ShadowLightVP.splitDistances`도 `float[7][4]`(원소당 [값, 패딩×3])로 맞춰 바이트 정합 유지.

| 파일 | 내용 |
|---|---|
| `Engine/_Shaders/DirectX/DeferredLighting.hlsl` | `gSplitDistances`: `float4[2]` → `float[MAX_CASCADE_COUNT-1]`. `GetSplitDistance(i)`: `gSplitDistances[i/4][i%4]` → `gSplitDistances[i]` |
| `Engine/Private/Render/DeferredLightingRenderer.cpp` | `CB_ShadowLightVP.splitDistances`: `float[8]` → `float[7][4]`(HLSL 스칼라 배열의 16바이트 패딩과 바이트 단위 정합). 업로드 루프가 `[s][0]`에만 값 기록 |

### Math 유틸 중복 제거

## Compact Log #7

### 그림자 찢김 근본 원인 — GetMatrixForward를 view 행렬에 잘못 적용(Compact Log #6 회귀)

**배경**: Compact Log #5의 `gSplitDistances` 이중 동적 인덱싱 수정 이후에도 사용자가 캐스케이드 4·7·8 전부에서 그림자 찢김이 재현됨을 보고(`ScreenShot/CSM_Bug6 (1)(2).png`) — "캐스케이드 수와 무관한 현상, 씬이 작아 낮은 수치에서는 관측 안 되는 것으로 추정"이라는 정확한 진단 힌트를 줌.

**1차 진단(기각)**: `ShowCascades` 비교(`CSM_Bug 7`) 결과 캐스케이드 0은 정상, 1 이상은 완전히 그림자가 안 나옴을 확인. `ComputeCascades`의 박스 계산을 의심해 캐스케이드별 (a) 자기 중심점 자기 정합성, (b) 서브 프러스텀 8코너 전체가 [0,1] UV/depth 안에 드는지 직접 투영해 확인하는 임시 진단(`ScreenShot/CSM_Bug 9.png`) 추가 — **결과: 전부 정상**(코너 U/V/D 전부 [0,1] 안쪽, 여유까지 있음). `ComputeCascades`의 bounding-sphere 계산은 처음부터 끝까지 결백이었음이 확정됨.

**결정적 단서**: 사용자가 카메라를 지면 위 66유닛, Pitch -80.1°(거의 수직으로 내려다보는 각도)까지 올려서 테스트(`ScreenShot/CSM_Bug 9 (2).png`) — 카메라 바로 아래, 실제로는 60~70유닛 떨어진(따라서 가장 먼 캐스케이드에 배정돼야 할) 바닥 전체가 **캐스케이드 0(빨강) 하나로만** 칠해짐. "거리가 얼마든 x,z가 중심에 가까우면 빨간색만 나온다"는 사용자 관찰이 정확히 이 현상을 가리킴.

**근본 원인**: `CalcShadowFactor`의 `camDist`(캐스케이드 선택 기준)를 만드는 `CameraForward`를 Compact Log #6에서 `Container.h::GetMatrixForward(cam.view)`로 교체했었는데, 이 함수가 **row 2**(`m[2][0], m[2][1], m[2][2]`)를 읽도록 만들어져 있었음. 이건 `WorldObject.cpp`의 월드 행렬(local→world, `RotationQuat` 등으로 구성)에는 맞는 인덱싱이지만, 카메라의 view 행렬(`LookAtLH`, world→view — **변환 방향이 반대**)에는 **틀린** 인덱싱이었음:

- `RotationQuat`(local→world): 로컬 X축(1,0,0)을 변환하면 결과가 **row 0**에 나옴 → 축은 row에 저장됨.
- `LookAtLH`(world→view, 반대 방향): row-vector 컨벤션(`v_out[j] = Σ v_in[i]·M[i][j]`)에서 `v_out.x = dot(v_in, column0)`이 되므로, forward(zAxis)는 **column 2**(`m[0][2], m[1][2], m[2][2]`)에 저장됨.

같은 `Matrix4x4` 타입이라 겉보기엔 "동일한 패턴"으로 보였지만, 실제로는 구성 방향이 반대라 row/column이 뒤바뀌는 근본적으로 다른 행렬이었음 — Compact Log #6에서 "일반화 가능한 중복"으로 잘못 판단해 `WorldObject.cpp`용으로 검증된 코드를 카메라 view 행렬에도 그대로 적용한 것이 회귀의 원인. `GetMatrixForward(cam.view)`가 실제로는 `(xAxis.z, yAxis.z, zAxis.z)`라는, 세 축의 Z성분을 뒤섞은 의미 없는 벡터를 반환하고 있었고, 이걸로 계산한 `camDist`가 사실상 무의미한 값이 되어 대부분 작은 값(캐스케이드 0)으로 잘못 분류된 것.

**수정**: `DeferredLightingRenderer.cpp`의 `CameraForward` 추출을 `GetMatrixForward(cam.view)` 호출에서 원래(Compact Log #6 리팩터링 이전)의 직접 column 인덱싱(`{ cam.view.m[0][2], cam.view.m[1][2], cam.view.m[2][2] }`)으로 되돌림. `Container.h`의 `GetMatrixRight/Up/Forward/Translation` 주석에 "local→world 행렬 전용, view 행렬에는 쓰면 안 됨" 경고를 명시적으로 추가해 재발 방지. `WorldObject.cpp`/`RenderScene.h`의 기존 사용(둘 다 local→world 행렬 대상)은 원래부터 올바른 사용이라 변경 없음.

**교훈**: "같은 `Matrix4x4` 타입이니 같은 패턴일 것"이라는 가정이 틀렸던 사례 — 일반화하기 전에 두 사용처가 정말 같은 의미론(여기서는 변환 방향)을 공유하는지 확인해야 했음. Compact Log #6에서 `UnprojectNDC`↔`ScreenToRay`의 중복은 진짜 동일 연산이라 통합이 맞았지만, `WorldObject`의 월드 행렬과 카메라의 view 행렬은 우연히 같은 코드 모양(`m[N][0..2]` 패턴)이었을 뿐 실제로는 다른 대상이었음 — "코드가 비슷해 보인다"와 "수학적으로 같은 연산이다"를 혼동하면 안 된다는 사례로 기록.

|---|---|

4. 1차 결과: 화면 전체가 마젠타(진단 코드의 "0~8 범위 밖" 색) — 5 이상만 확인했던 1차 진단(1~4만 구분)이 놓친 범위. 0~8 전체로 진단을 넓힘.
5. 2차 결과: **화면 전체가 검정(=0)**, 반면 C++ HUD 로그는 `activeCascadeCount(param)={n} shadowData.activeCascadeCount={n} offsetof=632 sizeof(CB_ShadowLightVP)=640` — C++은 항상 정확한 값을 정확한 오프셋(632)에 쓰고 있는데 GPU는 항상 0만 읽음. **C++ 쪽은 결백, GPU가 실제로 계산한 오프셋이 632가 아니라는 뜻.**

**근본 원인**: `gSplitDistances`를 `float4[2]` + 이중 동적 인덱싱에서 `float[MAX_CASCADE_COUNT-1]`(평범한 스칼라 배열, 단일 인덱싱)로 바꾼 것이 Compact Log #7의 수정이었는데, 이때 "HLSL cbuffer에서 스칼라 배열은 원소마다 16바이트(레지스터 하나)를 차지한다"고 가정하고 C++ 구조체도 `float[7][4]`(원소당 16바이트, `[x][0]`만 사용)로 맞췄었다. 그런데 실제 컴파일러는 스칼라 배열을 레지스터 하나에 4개씩 빽빽하게 채우는 방식으로 컴파일한 것으로 확인됨(7개 원소 → 32바이트, C++이 가정한 112바이트가 아님). 이 차이만큼 배열 뒤에 오는 `gShadowMapTexelSize/gBlendWidth/gActiveCascadeCount/_shadowPad`의 실제 GPU 오프셋이 C++ 구조체보다 앞당겨져, `gActiveCascadeCount`가 실제로는 C++이 `{}`로 항상 0 초기화해 두는 `splitDistances[s][1..3]` 패딩 영역을 읽고 있었다. Compact Log #7 당시 "이중 동적 인덱싱을 없애 버그가 고쳐졌다"는 결론은 맞았지만(그 자체는 진짜 컴파일러 불안정성이었음), 그 대체 레이아웃의 패딩 가정이 처음부터 틀려 있었던 것 — 별개의 두 버그가 우연히 겹쳐 있었다.

**수정**: `gSplitDistances`를 `float[MAX_CASCADE_COUNT-1]`에서 `float4[MAX_CASCADE_COUNT-1]`(원소당 16바이트가 타입으로 보장됨, `.x`만 사용하는 단일 인덱싱 유지)로 교체. `GetSplitDistance(i)`도 `gSplitDistances[i].x`로 수정. C++ 구조체(`CB_ShadowLightVP::splitDistances[7][4]`)는 이미 원소당 16바이트로 패딩되어 있어 변경 불필요 — HLSL 쪽만 타입으로 강제해 두 쪽의 실제 오프셋을 다시 일치시켰다.

**부수 효과**: 이 버그는 `gActiveCascadeCount`뿐 아니라 `GetSplitDistance()`가 읽는 split 경계값 자체도 잘못된 오프셋을 읽고 있었다는 뜻 — 캐스케이드 2개 이상일 때의 split 전환 지점도 이번 수정으로 같이 바로잡혔다(활성 캐스케이드 1개 테스트만으로는 이 경로가 실행되지 않아 이번 버그 재현에는 관여하지 않았음).

**교훈**: HLSL cbuffer의 스칼라 배열 패킹 규칙은 컴파일러/버전에 따라 직관과 다를 수 있어 신뢰하지 말 것 — 원소 크기를 보장받고 싶으면 스칼라 배열 대신 `float4` 등 실제 벡터 타입 + 단일 인덱싱(`.x`)으로 명시적으로 강제하는 편이 안전하다. Compact Log #7에서 "동적 이중 인덱싱을 없앴다"는 원인 규명이 정확했음에도, 그 대체 구현이 세운 새 가정(패딩 크기) 자체를 검증하지 않아 별개의 버그가 남아 있었던 사례.

**진단 방법론**: 화면 색상(GPU 최종 결과)만으로는 "C++이 잘못 보냈는지 / GPU가 잘못 읽었는지"를 구분할 수 없어, 셰이더 내부 값(gActiveCascadeCount)을 `SelectCascade` 등 중간 로직을 거치지 않고 직접 색으로 노출하는 최소 진단과, C++ 쪽 업로드 직전 값을 HUD로 동시에 출력하는 교차검증을 사용 — 이번 세션에서 반복 검증된 "숫자 그라운드 트루스가 육안 추측보다 낫다" 원칙의 연장.

**상태**: 근본 원인 확인·수정·육안 검증 전부 완료. 진단 코드(셰이더 색상 오버레이 + C++ HUD 로그) 전부 원복 후 재검증:
- 진단 단계: "단일 색상으로, hlsl debug color로 설정한대로 잘 보임" — GPU가 올바른 offset(632)을 읽음을 확인.
- 원복 후 실사용 검증: 활성 캐스케이드 2개 이상 — 색상 오버레이가 거리별로 정상 분할(부수 효과로 언급한 split 경계값 수정도 함께 검증됨). 활성 캐스케이드 1개 — 오버레이가 균일한 빨강(`kCascadeColors[0]`)만 표시, `SelectCascade`가 무조건 `cascade=0`을 반환하는 코드 로직과 정확히 일치하는 정상 동작.
