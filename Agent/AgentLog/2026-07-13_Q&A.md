## Q1. CSM 구현 방식 비교 — Atlas vs Texture2DArray Depth

### 비교표

| 항목 | Atlas (단일 큰 depth, viewport 4분할) | Texture2DArray depth (슬라이스당 DSV) |
|---|---|---|
| **RHI 변경** | 없음 — 기존 `DeclareTransientDepth` 그대로, CPU에서 `D3D12_VIEWPORT`만 캐스케이드별로 바꿔 Draw | `IDepthBuffer::Create()`에 arraySize 추가, DSV 힙을 N슬롯으로(슬라이스별 `D3D12_DSV_DIMENSION_TEXTURE2DARRAY`+`FirstArraySlice`), readOnly DSV도 N슬롯, SRV는 `TEXTURE2DARRAY` 1개로 전체 커버 — 이 엔진에 DSV-array 코드 전례 없음, 새로 작성 |
| **셰이더 샘플링** | atlas UV = `cascadeIndex`에 따른 scale+bias 오프셋 계산 필요 | `float3(uv, cascadeIndex)` — 인덱스만 넘기면 됨, 더 단순 |
| **PCF 시 캐스케이드 경계 bleeding** | 실재하는 위험 — PCF 커널이 atlas 영역 경계 근처 텍셀을 샘플링하면 옆 캐스케이드 텍셀을 섞어버림. 서브렉트 안으로 UV clamp 또는 패딩 보더 필요(추가 구현·검증 부담) | 구조적으로 불가능 — 배열 슬라이스는 물리적으로 분리된 서브리소스라 고정 인덱스 샘플링은 슬라이스 경계를 절대 넘지 않음 |
| **캐스케이드 개수 변경** | 그리드 레이아웃을 다시 짜야 함(4개=2×2는 쉽지만 3·5개는 정사각형 패킹이 애매) | `arraySize` 정수 하나만 바꾸면 됨 |
| **해상도 배분** | 총 해상도를 그리드로 나눠 가짐 — 비균등 배분(근거리 캐스케이드에 더 큰 해상도)을 하려면 직접 렉트 패킹 필요 | 슬라이스마다 독립적 — 비균등 배분도 슬라이스별 크기 지정으로 더 자연스러움 |
| **RenderGraph 상태추적 정합성** | 문제없음 | 문제없음 — 모든 슬라이스가 ShadowPass 동안 함께 DepthWrite였다가 함께 SRV로 전환되는 lockstep이라, 리소스 단위(서브리소스 단위 아님) 상태추적으로도 충분 |
| **구현 리스크** | 낮음 — 검증된 경로 재사용 | 신규 리소스 생성 경로 = OIT clear-value 버그·Stage A 트랜지언트 depth 상태 버그처럼 "처음 쓰는 조합에서 터지는 버그" 재발 가능성 |
| **디버깅(PIX/RenderDoc)** | 한 장의 2D 이미지로 통짜 확인 가능 | 슬라이스별로 봐야 함 |
| **총 메모리** | 동일 | 동일 |

### 결론 — Texture2DArray 채택

"목표 상태로 바로 구현, 리팩토링 없이 유지 가능한 구조" 원칙은 **엔진을 만드는 현재의 우리가 아니라, 이 엔진을 나중에 쓰는(확장하는) 대상을 향한 것**이라는 사용자 확인에 따라, 착수 난이도보다 구조적 정합성을 우선한다. Atlas는 PCF 커널 크기를 키울 때마다 패딩을 다시 검증해야 하는 "직접 만든 버그 위험"을 구조에 내장하는 반면, Texture2DArray는 그 위험을 물리적으로 차단한다. 초기 구현 비용이 더 들더라도 Texture2DArray Depth 방식으로 진행한다.

## Q2. Texture2DArray Depth 채택 시 예상 사이드 이펙트

### RHI 계층

1. **`IDepthBuffer::Create()` 시그니처 확장** — 현재 `Create()`는 인터페이스(`IDepthBuffer.h`)에 노출되지 않고 구현체(`DepthBuffer_DirectX.h`) 전용이다. `arraySize` 파라미터 추가 시 기본값 1로 기존 호출부(GBuffer 메인 depth, Stage A shadow depth)는 무변경 보장 가능.
2. **DSV 힙 확장** — 현재 `DepthBuffer_DirectX::Create()`(`DepthBuffer_DirectX.cpp:67-76`)는 1-slot private heap. 슬라이스별 DSV(`FirstArraySlice=i, ArraySize=1`)로 N-slot heap이 필요하고, readOnly DSV 힙(90-98행)도 동일하게 N슬롯으로 늘어남.
3. **`IDepthBuffer::GetView()` 계약 확장** — 현재(`IDepthBuffer.h:16`) 인자 없이 DSV 핸들 1개를 반환. 캐스케이드별 DSV를 구분하려면 `GetView(uint32_t slice = 0)`처럼 넓혀야 하는데, 이 인터페이스는 GBuffer 메인 depth 등 다른 소비자도 함께 쓰는 **공용 인터페이스**라 기본 인자로 하위 호환은 유지되지만 계약 자체가 넓어진다는 점은 고지할 필요.
4. **SRV는 변경 없음** — 배열 전체를 커버하는 `TEXTURE2DARRAY` SRV 1개로 충분해 `BindSRV` 시그니처는 그대로 재사용 가능(긍정적 요소).

### RenderGraph 계층

5. **`TransientDepthDesc`에 `arraySize` 필드 추가 필요**(`RenderGraph.h:21-26`) — 캐시 키 비교 로직(`DeclareTransientDepth` 구현부)이 이 필드까지 비교하도록 함께 고쳐야 §0-3 alias 방지 원칙이 유지됨. 빠뜨리면 같은 width/height/format의 비-array depth와 캐시가 혼동될 잠재 버그가 생김.
6. **캐스케이드 4장을 그리는 방식 결정 필요** — (a) `AddPass<...>`를 캐스케이드마다 4번 등록(Bloom의 BrightPass/BlurH/BlurV/Composite, OIT의 Accum/Composite처럼 "한 기능 = 여러 Pass 구조체"라는 기존 컨벤션과 일치) vs (b) Pass 1개의 `Execute()` 내부에서 슬라이스별 DSV로 4번 루프. (a)가 컨벤션에 더 맞지만 4개 Pass가 "같은 씬을 다른 시점에서 다시 그린다"는 중복 코드를 가지므로 공통 헬퍼로 묶는 설계가 필요.

### 셰이더/라이팅 계층

7. **광원 행렬 CB(root8) 구조 확장** — 현재 view-proj 행렬 1개 → 캐스케이드 4개분 행렬 + split distance 배열로 커짐. C++ CB struct와 HLSL cbuffer struct 양쪽 offset/padding을 함께 재계산해야 함 — Pre-1(Point/Spot 감쇠 CB 정리)에서 겪은 것과 동일한 종류의 정합성 리스크.
8. **캐스케이드 선택 로직 신규 필요** — 픽셀이 어느 캐스케이드에 속하는지 고르는 분기(Stage A엔 없던 로직). Atlas를 택했어도 동일하게 필요한 공통 비용이지만, PCF 샘플링이 `SampleCmpLevelZero(sampler, float3(uv, cascadeIndex), depth)` 형태로 바뀌는 지점은 Array 고유 구현.
9. **캐스케이드 전환 경계(seam)는 Array를 택해도 남는 문제** — PCF 커널의 atlas-bleeding은 Array가 구조적으로 막아주지만, split distance 근방에서 그림자 품질이 갑자기 달라지는 현상 자체는 별개 문제라 여전히 발생 가능. 통상 인접 캐스케이드 blend/dither로 완화하는데, 이번 범위엔 없어 기술부채로 남을 가능성이 높음. → [Q4](#q4-cascade-blenddither를-기술부채로-남기지-않고-해결-가능한가)에서 blend는 이번 범위에 포함하기로 결론.

### 기존 기능과의 상호작용

10. **스키닝 메시 shadow caster 비용 4배** — 이미 완료된 `ShadowMapRenderer::InitializeSkinned`도 캐스케이드마다 다시 그려야 함. PSO는 재사용 가능하나 Kachujin처럼 스키닝 캐릭터가 캐스터인 씬에서 드로우 횟수가 그대로 4배로 늘어남.
11. **CPU 드로우콜 4배** — 캐스케이드별 프러스텀 컬링이 없으면 매 캐스케이드마다 전체 씬을 다시 순회. 지금 씬 규모(오브젝트 수 적음)에선 무시 가능하나, 오브젝트가 늘어나는 시점엔 별도 최적화(캐스케이드별 컬링) 필요 — 기술부채 후보로 기록할 가치. → [Q3](#q3-atlas로-진행하면-드로우콜-증가를-막을-수-있는가)에서 저장 방식(Atlas/Array)과는 무관한 별개 문제임을 확인.
12. **"Transparent 패스 shadow 미적용" 부채가 그대로 유지** — CSM 도입 후에도 해소되지 않고, 나중에 이 부채를 풀 때 Transparent.hlsli에 캐스케이드 선택 로직까지 함께 이식해야 하므로 해결 비용이 소폭 커짐.

### 긍정적 side effect

13. **전역 SRV 힙(1024 슬롯) 소비 변화 없음** — DSV는 별도 private heap이라 전역 힙 예산과 무관, SRV는 배열이든 아니든 1슬롯.
14. **Root Signature 슬롯 수 변화 없음** — shadowDepth SRV(root7)는 여전히 1개 슬롯, 광원행렬 CB(root8)는 in-place 확장이라 append 전략을 새로 쓸 필요 없음.

## Q3. Atlas로 진행하면 드로우콜 증가를 막을 수 있는가

### 결론 — 아니오, 저장 방식과 무관한 별개 문제

Atlas와 Array는 "셰도우 depth 결과를 어떻게 저장하느냐"의 선택이고, "씬을 몇 번 제출하느냐"와는 무관하다. CSM은 저장 방식과 상관없이 캐스케이드마다 다른 view-proj로 깊이를 다시 그려야 해서, Atlas를 택해도 N번(캐스케이드 수)만큼 씬을 순회하는 구조 자체는 그대로 남는다.

### 드로우콜 수 자체를 줄이는 실제 기법 — GPU 인스턴싱

오브젝트당 드로우 1번을 캐스케이드 수만큼 인스턴스화(`SV_InstanceID`로 캐스케이드별 view-proj 선택)하고, VS에서 `SV_ViewportArrayIndex`(Atlas의 서브렉트 선택) 또는 `SV_RenderTargetArrayIndex`(Array의 슬라이스 선택)를 출력해 GPU가 라우팅하게 하는 방식.

- CPU 드로우콜 기록 비용만 줄어들 뿐, GPU가 처리하는 정점/래스터화 총량은 그대로(캐스케이드 수만큼 여전히 처리) — "CPU 커맨드 기록 비용"만 줄이는 것이지 "GPU 셰도우패스 총 비용"을 줄이는 게 아님.
- 전제조건: 하드웨어가 VS단에서 `SV_ViewportArrayIndex`/`SV_RenderTargetArrayIndex` export를 지원해야 함(`D3D12_FEATURE_DATA_D3D12_OPTIONS3`). 지원 안 되면 Geometry Shader pass-through가 필요한데, 이 엔진은 현재 GS 스테이지를 아예 쓰지 않음(전 파이프라인 VS+PS 구조).
- **Atlas를 고르면 딸려오는 공짜 이점이 아니라, 그 자체로 별도 결정이 필요한 독립적인 기법** — Atlas·Array 둘 다에 적용 가능한 최적화이지, Atlas 고유의 장점이 아니다.

### 현실적인 완화책 — 캐스케이드별 프러스텀 컬링

각 캐스케이드가 실제로 덮는 오브젝트만 그 캐스케이드에 제출. 저장 방식과 무관하게 항상 적용 가능하고, 오브젝트 수가 늘어나는 시점에 표준적으로 쓰는 최적화. 지금 씬 규모에선 우선순위가 낮아 기술부채로 기록만 해둔다(Q2 항목 11).

## Q4. Cascade Blend/Dither를 기술부채로 남기지 않고 해결 가능한가

### Dither — 이번 범위에서 제외

Dither는 경계의 노이즈를 시간축으로 뭉개주는 TAA(temporal accumulation)가 있어야 자연스럽다. 이 엔진엔 TAA가 없어, TAA 없이 dither만 넣으면 경계에 그대로 노이즈 패턴이 보여 오히려 품질이 나빠진다. TAA 자체가 CSM보다 훨씬 큰 별도 과제라 지금 포함하지 않는다.

### Smooth Blend(lerp) — 이번 범위에 포함

캐스케이드 선택 로직 자체가 CSM 구현에 어차피 필요하므로(Q2 항목 8), 경계 근방에서 "현재 캐스케이드 + 다음 캐스케이드"를 둘 다 샘플링해 `saturate((viewDepth-splitStart)/blendWidth)`로 lerp하는 정도는 새 리소스·바인딩 슬롯 없이 셰이더 로컬 추가로 끝난다. CB에 `blendWidth` 튜닝 값 하나만 늘어난다.

- 대가: 경계 근방 픽셀에서 PCF 비교 샘플링이 2배(현재+다음 캐스케이드) — 국소적 비용, 전체 프레임 비용 영향은 작음.
- `blendWidth`는 IBL 클램프·SSAO 반경·OIT weight function처럼 육안 튜닝이 필요한 매직넘버가 될 가능성이 높음.

### 결론

Dither는 제외(TAA 선행 필요), Smooth Blend는 캐스케이드 선택 로직에 자연스럽게 얹히는 확장이라 기술부채로 미루지 않고 이번 CSM 구현에 함께 포함한다.

## Q5. Geometry Shader·Hull Shader 도입 피드백

### 전제 확인

`Engine/_Shaders` 전체 검색 결과 GS/HS/DS(Geometry/Hull/Domain Shader) 코드가 전혀 없고, `CheckFeatureSupport`류의 D3D12 기능 조회 코드도 없음. 지금 도입한다면 기존 확장이 아니라 RHI에 새 셰이더 스테이지 카테고리를 처음부터 만드는 일이다.

### 권장하지 않음 — 근거

1. **GS는 Q3 드로우콜 최적화의 "폴백"일 뿐, 주 경로가 아님** — `SV_ViewportArrayIndex`/`SV_RenderTargetArrayIndex`는 VS 단에서 GS 없이 직접 export 가능하고, 이 프로젝트 디버그 로그에 실제로 찍혔던 Intel Gen12LP를 포함해 최신 하드웨어는 대부분 이 기능(`VPAndRTArrayIndexFromAnyShaderFeedingRasterizerSupportedWithoutGSEmulation`)을 지원한다. GS는 이 기능이 없는 구형 하드웨어용 우회로라, 지금 타겟에서 필요할 가능성이 낮다.
2. **GS 자체가 성능 안티패턴** — 프리미티브 증폭/라우팅이 대부분의 IMR 하드웨어에서 프리미티브 레이트 병목을 일으켜, 업계가 GS를 버리고 컴퓨트 기반 증폭이나 VS 단 array-index export로 옮겨간 이유. 드로우콜을 줄이자고 GS를 넣으면 CPU 비용을 GPU 프리미티브 처리 비용으로 맞바꾸는 셈이라 순이익이 불확실.
3. **HS는 이 문제와 무관** — Hull Shader는 패치 테셀레이션(지형 디테일 등) 제어용이지, 프리미티브를 다른 뷰포트/RT 배열 슬라이스로 라우팅하는 것과 관계없음. CSM 드로우콜 문제 해결에 HS가 낄 자리가 없음.
4. **멀티플랫폼 역효과** — CLAUDE.md의 플랫폼 표가 "ExecuteIndirect·Compute Culling은 TBDR에서 대역폭 역효과"라고 명시하는데, GS는 Vulkan `geometryShader`가 optional feature라 모바일 TBDR GPU에서 아예 없거나 있어도 더 느림. Forward 선호 방향과 정면 배치.
5. Q3에서 확인했듯 드로우콜 4배 자체가 지금 씬 규모에선 우선순위 낮은 기술부채 — 아직 병목으로 확인되지도 않은 문제를 풀겠다고 RHI에 셰이더 스테이지 카테고리를 통째로 새로 만드는 건 비용 대비 이득이 없음.

### 결론

GS/HS 도입에 반대. 드로우콜이 실측으로 병목임이 확인되면 GS 없이 VS 단 array-index export만 검토(그마저도 CSM 최초 구현 범위엔 넣지 않음).

## Q6. CSM이 적용되면 좋은 이유

### Mip Level과 CSM — 개념적 유사성과 구조적 차이

이번 CSM 재검토가 "mip level이 생겼으니 가능한가"라는 질문에서 시작됐으므로, 왜 둘이 비슷해 보이면서도 실제로는 다른 메커니즘인지 명확히 정리한다.

**개념적으로는 같은 원리를 공유한다** — 둘 다 "한정된 해상도 예산을 지각적으로 중요한 곳에 몰아준다"는 그래픽스의 공통 원칙을 따른다. 다만 적용 방향이 정반대다.

| 구분 | Mip Level | CSM Cascade |
|---|---|---|
| **무엇의 LOD인가** | 텍스처 샘플링(읽기) | 셰도우 렌더링(광원 시점에서 매 프레임 다시 그림) |
| **데이터 생성 방식** | 원본 텍스처를 다운샘플링(필터링)해 미리 구워둠 — 같은 이미지의 해상도만 다른 사본 | 광원 시점에서 서로 다른 Orthographic 투영 박스로 씬을 매번 다시 래스터화 — 해상도는 보통 동일, 담고 있는 뷰 볼륨(투영 범위)이 서로 다름 |
| **레벨 간 관계** | 계층적 — mip1은 mip0을 절반으로 줄인 것, 서로 보간(trilinear) 가능 | 독립적 — 캐스케이드 0과 1은 서로 다른 카메라 프러스텀 구간을 담은 별개의 이미지, 보간 대상이 아니라 선택 대상(Q4의 seam blend는 예외적으로 인접 캐스케이드를 섞는 경우) |
| **해상도 재분배 방향** | 화면에서 작게 보이는(먼) 표면에 자동으로 낮은 해상도를 할당 — 언더샘플링으로 인한 시각적 노이즈(moire) 방지 | 카메라에서 가깝게 보이는 영역에 수동으로 높은 해상도를 할당 — 텍셀이 커 보여 그림자 가장자리가 계단지는 현상 방지 |
| **선택 기준** | 화면상 텍셀 밀도(스크린 공간 미분값)로 자동 선택, 또는 IBL처럼 셰이더가 roughness 값으로 연속 보간 선택 | 픽셀의 뷰 스페이스 깊이를 split distance와 비교해 셰이더가 명시적으로 분기/인덱싱 |
| **이 엔진의 RHI 지원 현황** | `ITextureUAV`에 이미 있음(IBL prefiltered map이 사용 중) | `IDepthBuffer`엔 없음(Q1~Q2에서 확인) — 새로 만들어야 함 |

**결론**: mip level은 "같은 이미지를 얼마나 흐리게 읽을지"를 고르는 텍스처 샘플링 기법이고, CSM은 "어느 투영 박스로 다시 그릴지"를 고르는 렌더링 기법이다. 두 기법이 푸는 문제(해상도 예산의 비효율적 분배)는 같은 뿌리를 갖지만, 구현 층위(읽기 vs 쓰기)와 데이터 구조(다운샘플 계층 vs 독립 투영 집합)가 달라 한쪽의 RHI 지원이 다른 쪽으로 자동 이전되지 않는다.

### Stage A의 자체 한계 — 고정 박스 근사

`Plan_RenderQuality.md`에 이미 명시된 한계: "고정 박스 근사, 씬 바운드 추적 없음". 지금은 2048×2048 텍셀 예산을 화면에 보이는 전체 깊이 범위(카메라 바로 앞부터 저 멀리까지)에 통째로 펼쳐 쓴다.

### CSM이 개선하는 지점

- **텍셀 밀도 균일 → 거리별 집중**: 지금은 근거리(aliasing이 가장 눈에 띄는 구간)와 원거리가 같은 텍셀 밀도를 나눠 가져 가까운 오브젝트 그림자 가장자리가 계단져 보임. CSM은 같은 2048² 예산을 캐스케이드마다 훨씬 좁은 월드 영역에 집중시켜, 근거리 캐스케이드의 텍셀 밀도를 급격히 올리고(그림자가 또렷해짐) 원거리는 낮은 밀도로도 시각적으로 덜 민감해 손해가 적음.
- **고정 박스 크기 트레이드오프 해소**: 지금은 박스를 작게 잡으면 카메라 이동 시 그림자가 잘리고, 크게 잡으면 전체 품질이 떨어지는 딜레마가 있음. CSM은 근거리 캐스케이드가 카메라를 바짝 따라가며 작고 또렷하게, 원거리 캐스케이드는 넉넉하게 잡아 두 목표가 같은 텍셀 예산을 두고 경쟁하지 않음.
- **씬 확장에도 품질 일관성 유지**: Scene Scale 전환·WorldObject Hierarchy 작업 이후 콘텐츠가 늘어나는 방향에서, 손으로 튜닝한 고정 박스 하나로 버티는 대신 매 프레임 카메라 프러스텀에 맞춰 재적합되어 품질이 일관되게 유지됨.

### 정직한 한계

Point/Spot 그림자 부재, Transparent forward shadow lookup 부재는 CSM 도입 후에도 그대로 남고(Q2 항목 12), Q4의 seam blend 비용이 새로 추가됨. 그래도 Stage A가 스스로 "근사"라고 명시한 지점을 정확히 겨냥해 고치는 표준적이고 검증된 기법이라는 점에서 적용 근거는 명확함.

## Q7. 상용 엔진의 텍스처 Mip/LOD 조정은 어떤 방식인가

캐스케이드 개수 가변화 논의에서 나온 "최대치로 미리 할당해두고 활성 개수만 런타임에 조절" 패턴이 상용 엔진의 텍스처 mip/LOD 조정과 같은 방식인지에 대한 질문. 실제로는 성격이 다른 세 메커니즘이 "mip/LOD 조정"이라는 이름 아래 섞여 있음.

### 1. 텍스처 Mip Bias/Clamp — 리소스 재할당 없음

게임 옵션의 "텍스처 품질 Low/Medium/High"가 대부분 이 방식. 텍스처는 임포트 시점에 이미 전체 mip 체인이 만들어져 있고, 런타임에 바뀌는 건 샘플러의 `MipLODBias`/`MinLOD`/`MaxLOD` 값 하나뿐 — 리소스 자체는 손대지 않는 순수 샘플러 파라미터 튜닝. 이 엔진의 IBL prefiltered map(`kPrefilterMipLevels=5`)이 이 방식에 해당 — 5개 밉을 전부 만들어두고 roughness로 `SampleLevel`이 어느 밉을 읽을지 정할 뿐, 밉 개수 자체는 안 바뀜.

### 2. Mesh LOD(지오메트리 디테일 단계) — 캐스케이드 제안과 정확히 동일한 패턴

LOD0(풀 디테일)~LOD3(저폴리) 각각이 완전히 별개의 정적 메시 리소스로 미리 만들어져 있고, 런타임엔 카메라 거리·화면 점유율로 "몇 번 LOD를 그릴지"만 인덱스로 고름. "미리 만들어둔 개수" = 최대치, "실제 그리는 개수" = 활성치라는 구조가 캐스케이드 제안(최대치 할당, 활성 개수는 그 이하)과 완전히 일치.

### 3. 텍스처 스트리밍 — 더 정교한 버전

UE Virtual Texturing/Unity Texture Streaming은 텍스처의 모든 밉을 항상 VRAM에 올려두지 않고, D3D12 Reserved(Tiled) Resource로 가상 주소만 예약한 뒤 실제로 필요한 밉에만 물리 메모리 타일을 붙였다 뗐다 함. "최대치를 통째로 커밋"하는 방식보다 메모리 효율이 훨씬 좋지만 `CreateReservedResource`/`UpdateTileMappings` 등 별도 API가 필요한 큰 기능.

### 결론

캐스케이드 개수는 2번(Mesh LOD) 방식이 정확한 비유이며, 3번(타일드 리소스)까지 갈 필요는 없다고 판단. 캐스케이드 최대 8장 정도면(2048² D24S8 기준 슬라이스당 ~16MB, 8장 전부 상주시켜도 ~128MB) 이 프로젝트 규모에서 상시 커밋 부담이 크지 않음. 다만 "항상 최대치만큼 VRAM을 먹는다"는 트레이드오프는 실제 구현 시 고지 필요.
