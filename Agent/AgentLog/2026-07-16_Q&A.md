## Q1. 프러스텀 컬링 전략 비교 — GPU 클리핑에 의존 vs CPU 사전 필터링

### 질문

- (A) CPU에서 씬의 모든 오브젝트를 그대로 GPU에 제출하고, 절두체 외부는 GPU가 알아서 연산을 끝낸다.
- (B) CPU에서 렌더링되어야 하는 자원만 먼저 판별(컬링)한 뒤, 절두체 내부의 오브젝트만 GPU에 제출한다.

둘 중 무엇이 더 나은가.

### 전제 정정 — GPU 클리핑은 "절두체 외부 오브젝트의 연산을 끝낸다"는 의미가 아님

래스터라이저 파이프라인의 클리핑은 절두체를 넘어가는 **프리미티브(삼각형)** 를 근/원/좌우 clip plane 기준으로 잘라내는 하드웨어 고정 기능이지, "이 오브젝트는 안 보이니 건너뛰자"는 조기 종료가 아니다. Draw call이 CPU에서 GPU로 제출되면:

- **Vertex Shader는 절두체 안팎과 무관하게 제출된 정점 전부에 대해 무조건 실행된다** — 클리핑은 VS 실행 결과(clip space 좌표)에 대해 그 이후에 일어나는 단계다.
- **Draw call 자체의 CPU 제출 비용**(Command List 기록, API 오버헤드)도 절두체와 무관하게 그대로 발생한다.
- 클리핑이 절약하는 것은 오직 "절두체에 걸쳐 있는 프리미티브의 래스터화 대상 프래그먼트 개수"뿐이다. **완전히 절두체 밖에 있는 오브젝트라도 VS 호출·draw call 비용은 100% 그대로 낸다.**

즉 (A)가 전제하는 "GPU에서 절두체 외부면 그대로 연산 종료"는 실제로 존재하지 않는 최적화다. 클리핑은 절두체 경계에 걸친 프리미티브를 위한 보정 기능이지, 완전히 화면 밖에 있는 오브젝트를 건너뛰는 컬링의 대체재가 아니다.

### 비교

| | (A) CPU 컬링 없이 전부 제출 | (B) CPU 사전 필터링 후 제출 |
|---|---|---|
| Draw call 수 | 오브젝트 수만큼 항상 고정 | 절두체와 교차하는 오브젝트만 |
| VS 호출 비용 | 화면 밖 오브젝트도 전부 지불 | 화면 밖 오브젝트는 0 |
| CPU 비용 | 없음(테스트 자체가 없음) | 오브젝트당 바운딩 볼륨-평면 교차 테스트(구 vs 6평면이면 내적 6회 수준) |
| 확장성 | 오브젝트 수 증가 시 GPU 부담이 그대로 선형 증가 | 씬이 커질수록(오픈월드 등) 이득이 커짐 |
| 이 엔진에서의 현재 상태 | `RenderScene.h` 확인 결과 이미 이 상태(전량 무조건 제출) | `RenderCommand`에 바운딩 볼륨 필드가 없어 신규 구현 필요 |

### 결론 — (B) CPU 사전 필터링이 표준이고 더 낫다

바운딩 볼륨-평면 교차 테스트는 오브젝트당 몇 번의 내적 연산 수준이라, 완전히 화면 밖에 있는 오브젝트의 draw call 제출과 VS 실행을 통째로 아끼는 이득이 압도적으로 크다. "GPU가 알아서 걸러준다"는 (A)의 전제 자체가 성립하지 않으므로(클리핑은 draw call 이후 개별 프리미티브 단위로만 작동), 실질적인 비교는 "교차 테스트 비용 vs 통째로 낭비되는 draw call·VS 비용"이고 후자가 항상 크다.

멀티플랫폼 관점에서도 CPU 컬링이 유리하다. CLAUDE.md에 명시된 대로 ExecuteIndirect·Compute 기반 GPU-Driven 컬링은 TBDR(ExecAndroid/Vulkan)에서 대역폭 역효과가 있어 쓸 수 없는 반면, CPU 프러스텀 컬링은 API·GPU 아키텍처와 무관하게 IMR(DX12)·TBDR(Vulkan) 양쪽에서 동일하게 이득을 낸다 — 이 엔진의 "알고리즘 선택과 API 선택은 독립적" 원칙과도 부합하는, 플랫폼에 무관한 기본기다.

### 현재 상태와 필요 작업

`RenderScene.h` 확인 결과 `RenderCommand`(72-85행)에는 바운딩 볼륨(AABB/Sphere) 필드가 없고, `BaseCamera` 쪽에도 프러스텀 평면 추출 로직이 없다. 즉 지금은 (A)/(B) 어느 쪽도 아니라 **컬링 자체가 없는 상태**(전부 제출, 클리핑에만 의존)다. `AddMesh`/`AddSkinnedMesh`(116-164행)는 들어온 오브젝트를 조건 없이 `commands`에 push하고, `CalculateSortKey`가 계산하는 `depth`는 draw *순서*(오버드로 최소화·알파 블렌딩)를 위한 것이지 컬링 판정이 아니다.

CPU 컬링을 도입하려면:
1. `WorldObject` 또는 `RenderCommand`에 바운딩 볼륨 데이터(AABB/Sphere) 추가.
2. `BaseCamera`/`RenderScene`에 6-평면 프러스텀 추출 로직 추가.
3. `AddMesh`/`AddSkinnedMesh` 시점(또는 그 앞단)에 교차 테스트를 거쳐, 컬링된 오브젝트는 `commands`에 아예 넣지 않는 필터링 단계 추가.

씬 규모가 커지기 전까지는 우선순위가 낮을 수 있다 — `2026-07-13_Q&A.md` Q3에서도 CSM 캐스케이드별 컬링을 "지금 씬 규모(오브젝트 수 적음)에선 무시 가능, 기술부채로 기록만" 결론으로 남긴 바 있어 같은 판단 기준이 적용된다. 다만 실제로 구현한다면 위 3단계가 방향이다.

## Q2. 멀티스레드 CPU 컬링 — 브루트포스 vs Loose-Octree

### 배경

Desktop(GPU compute)과 별개로 Mobile(ExecAndroid/Vulkan, TBDR)에서 쓸 CPU-Driven 컬링 경로를 별도로 설계한다. 그 CPU 경로 내부에서 "브루트포스"와 "loose-octree" 중 무엇을 쓸지 비교한 결과.

### 전제(가정)

- CPU-Driven 컬링 경로에 한정한 비교다 — GPU-Driven(Desktop 컴퓨트 셰이더) 컬링은 GPU 상주 버퍼·`ExecuteIndirect` 기반이라 구조 자체가 달라 이 비교의 대상이 아니다.
- **두 방식 모두 멀티스레드로 병렬화되어 있다는 전제**에서 비교한다(단일 스레드 비교가 아님).
- 오브젝트는 `WorldObject::AddToScene()`으로 매 프레임 재제출되는 현재 엔진의 즉시 모드(immediate-mode) 제출 패턴이 전제다 — `RenderScene::Clear()`(`RenderScene.h:180-184`)가 매 프레임 `commands`를 비우고 다시 채운다.
- 확인 결과 현재 엔진엔 멀티스레딩 인프라(스레드풀/Job System), 바운딩 볼륨 데이터, 프러스텀 평면 추출 로직이 전혀 없다 — 두 방식 모두 그린필드에서 시작한다는 전제.

### 비교표

| | 브루트포스 (병렬) | Loose-Octree (병렬) |
|---|---|---|
| **자료구조** | 평탄한 배열(SoA 권장: center.x/y/z, radius 분리) | 계층 트리, 노드마다 "느슨한"(보통 2배) 바운드로 경계 straddle 시 재삽입 빈도 완화 |
| **알고리즘 복잡도** | O(N) 항상 | 평균 O(log N + K), K=가시 오브젝트 수 — 화면 밖 공간이 넓을수록 유리 |
| **병렬화 난이도** | 쉬움 — 배열을 스레드 수만큼 균등 분할, 결과를 서로 겹치지 않는 영역에 쓰면 락 불필요 | 어려움 — 상위 몇 레벨에서 서브트리 단위로 fork-join 태스크 분배 필요. 서브트리마다 오브젝트 밀도가 달라 정적 분할 시 부하 불균형 → work-stealing 잡 시스템 필요 |
| **캐시 지역성** | 매우 좋음 — 순차 접근, prefetcher 친화적, SIMD로 4/8개씩 평면 테스트 묶어서 처리 가능 | 나쁨 — 포인터 기반이면 노드 방문마다 랜덤 접근. 완화하려면 Morton code 기반 "linear octree"(포인터 대신 배열/해시맵)로 구현 필요 |
| **동시성 안전성** | 문제 없음 — 읽기 전용 배열 스캔 | 까다로움 — 컬링 스레드가 트리를 읽는 동안 오브젝트가 움직여 재삽입되면 경합 발생. 보통 프레임 시작 시 바운드를 스냅샷 떠서 컬링 중엔 트리를 불변으로 취급해 해결 |
| **유지보수 비용** | 없음 — 배열에 추가/제거만 하면 됨(현재 엔진의 즉시 모드 제출 패턴과 자연히 맞음) | 있음 — 오브젝트 이동 시 삽입/삭제/재배치 비용이 매 프레임 추가로 발생. 동적 오브젝트가 많으면 컬링 절감분을 상쇄할 수 있음 |
| **구현/디버깅 난이도** | 낮음 | 높음 — 삽입/삭제/균형 로직 필요. 다만 기존 `DebugLineRenderer`로 노드 경계를 시각화하면 디버깅과 포트폴리오 데모를 겸할 수 있음 |
| **유리한 상황** | N이 작거나, 오브젝트가 화면에 고르게 분포(대부분 보임) | N이 크고 씬이 넓은데 카메라 시야가 좁아 대부분 화면 밖(오픈월드형) |
| **시연 가치** | "기본기가 된 병렬 job 처리" 시연 | 재귀적 fork-join, work-stealing, 동시성-안전 트리 같은 더 상급 멀티스레딩 패턴 시연 |

### 결론

순수 성능만 보면 지금 씬 규모(오브젝트 수 적음)에선 SIMD+멀티스레드 브루트포스가 loose-octree보다 오히려 더 빠를 수 있다 — 트리 순회의 포인터 체이싱 오버헤드가 방문 노드 수 감소분을 못 이길 정도로 N이 작을 가능성이 크다. 다만 "다양한 자료구조·병렬 패턴을 보여준다"는 포트폴리오 목적이 명시적으로 있으므로, 순수 성능 비교와 별개로 두 방식을 모두 구현해 스위칭·벤치마크 비교 결과 자체를 산출물로 남기는 방향이 목적에 부합한다.

가장 중요한 미해결 설계 질문은 loose-octree의 **영속성**이다 — 현재 제출 패턴(매 프레임 전체 재제출)을 그대로 따라 옥트리도 매 프레임 처음부터 다시 삽입하면, "노드 단위로 건너뛰어 테스트 횟수를 줄인다"는 이득은 유지되지만 "삽입 비용 자체를 아낀다"는 이점은 사라진다. 옥트리의 이점을 온전히 살리려면 `WorldObject` 생성/삭제/이동 시점에 훅을 걸어 증분 갱신하는 영속 구조로 만들어야 하는데, 이는 `RenderScene`이 매 프레임 `Clear()`되는 현재 구조와 어긋나 별도 저장 위치가 필요하다(→ 다음 논의 대상).

## Q3. 컬링 바운딩 볼륨 통일 여부 재검토

### 질문

컬링용 Sphere와 Collider(Phase 4-3)용 Capsule을 별도로 두면 오브젝트당 바운딩 볼륨을 두 개 유지하는 셈이라 메모리 낭비 아닌가? 차라리 Capsule 하나로 통일하는 게 낫지 않은가.

### 반박 — 전제 자체가 서로 다른 두 모집단을 하나로 착각한 것

Sphere는 씬에 그려지는 **모든** 오브젝트가 필요로 하고, Capsule은 그중 **충돌 판정이 실제로 필요한 일부**(M ≪ N, 대부분의 씬에서 충돌체는 소수)만 필요로 한다. "오브젝트 하나에 도형 두 개"가 아니라 "전체 N에 Sphere + 부분집합 M에 Capsule"이므로, Capsule로 통일(전체 N에 Capsule)하면 오히려 총 메모리가 늘어난다.

### 메모리 계산

- Sphere: `center(12B)+radius(4B)` ≈ 16B
- Capsule: `pointA(12B)+pointB(12B)+radius(4B)` ≈ 28B (Sphere 대비 약 2배)
- 분리 방식 총량: `16×N + 28×M`
- 통일 방식 총량: `28×N`
- M≪N인 한 통일 방식이 항상 더 크다. Phase 2의 스트레스 테스트 씬(오브젝트 N개 그리드 스폰)처럼 N이 커질수록 차이도 커진다.

### 메모리보다 더 중요한 문제 — 컬링은 매 프레임 도는 hot path

Capsule-vs-평면 테스트는 선분(두 끝점)을 다뤄야 해 Sphere-vs-평면 테스트(내적 1회)보다 연산량이 최소 2배 든다. 매 프레임·매 오브젝트·6평면에 대해 도는 컬링 경로에서 이 차이는 실측 가능한 성능 손해이며, Phase 2 자체의 목적(성능 비교를 수치로 보여주는 것)과 정면으로 배치된다.

### 형태 적합성

Capsule은 사람처럼 세장형(elongated) 형태에나 잘 맞는다. 바닥·타워·큐브처럼 Capsule 형태가 아닌 오브젝트를 억지로 Capsule로 감싸면 헐렁하게 감싸지거나(컬링 정밀도 손해) 축·반지름을 따로 계산하는 로직이 추가로 필요하다. Sphere는 메시 형태와 무관하게 "중심+최대거리"로 기계적으로 계산 가능하다.

### 같은 오브젝트라도 결국 두 개가 필요해질 가능성

렌더링+충돌 둘 다 필요한 오브젝트(캐릭터 등)도, 컬링용 바운드(애니메이션 중 동작 범위까지 포함해 "실제로 보이는 걸 놓치지 않도록" 안전하게 과대 근사)와 충돌용 Capsule(게임플레이 판정 느낌에 맞게 타이트하게 튜닝)은 목적 자체가 달라 크기가 다르다. Capsule 하나로 합쳐도 결국 서로 다른 크기의 Capsule 두 개가 필요해질 가능성이 높아, 메모리 절약 효과는 사라지고 컬링 비용만 비싸진 상태로 귀결된다.

### 결론 — Sphere(컬링) + Capsule(Collider) 분리 유지 확정

메모리·성능·형태 적합성 세 방향 모두 분리 쪽이 유리하다는 근거로, Sphere 유지가 최종 확정됐다. `Plan_Phase2.md` 1-6에 기록된 방향 그대로 유지.

## Q4. GPU-Driven 컬링 — 카운터 버퍼 분리 여부와 리셋 방식

### 질문

GPU-Driven 컬링의 컴퓨트 셰이더가 가시 오브젝트를 압축(compaction)할 때 쓰는 카운터에 대해 두 가지:
1. 카운터용 버퍼를 압축 결과(인다이렉트 draw args) 버퍼와 분리할지, 하나로 합칠지
2. 카운터를 매 프레임 0으로 리셋할 때 새 RHI 메서드(`ClearUnorderedAccessViewUint`)를 추가할지, 다른 방법으로 할지

### 결론 1 — 카운터 버퍼는 별도 리소스로 분리

| | 분리 | 통합(같은 버퍼에 카운터+args) |
|---|---|---|
| 매 프레임 리셋 | 4바이트짜리 작은 버퍼만 건드림 | 큰 버퍼 안 특정 오프셋만 리셋 — 결국 같은 일인데 위치 관리가 추가됨 |
| `ExecuteIndirect`의 `countBuffer` 인자 | 버퍼 그대로, offset 0 | 같은 버퍼를 오프셋 지정해 넘김 — 오프셋 계산이 하나 더 생김 |
| UAV 슬롯 바인딩 | u0=args, u1=counter로 명확히 분리 | 하나의 리소스를 두 용도로 써서 셰이더 쪽도 구조체 오프셋으로 나눠 접근해야 함 |
| Shadow 컬링 확장(캐스케이드 8개) | 캐스케이드별로 독립된 카운터를 하나씩 더 두면 됨 | 하나의 버퍼 안에 8개 카운터+8개 args 구간을 다 배치해야 해서 레이아웃이 복잡해짐 |

통합해서 얻는 이득(리소스 개수 하나 줄임)이 크지 않은 반면 분리의 이득이 뚜렷해 분리로 확정.

### 결론 2 — 리셋용 새 RHI 메서드 추가 안 함, 1-스레드 컴퓨트 셰이더로 대체

**핵심 근거 — D3D12 `ClearUnorderedAccessViewUint`의 API 특이사항**: 이 함수는 `D3D12_GPU_DESCRIPTOR_HANDLE`(shader-visible 힙)과 `D3D12_CPU_DESCRIPTOR_HANDLE`(CPU 전용 힙)을 **동시에** 요구한다 — 같은 UAV를 가리키는 핸들 두 개가 필요한 D3D12 API 자체의 예외적인 요구사항. 이 엔진의 `IResourceView`는 지금까지 "뷰 하나 = 핸들 하나"라는 전제로 설계돼 있어(`SetComputeUAV`/`SetGraphicsSRV` 등 전부 뷰 하나만 받음), 이 메서드를 제대로 추가하려면 `IResourceView`를 확장하거나(모든 SRV/UAV 소비자에 영향) DX12 백엔드 내부에 이 메서드만을 위한 특수 케이스(CPU 전용 힙에서 추가 핸들 할당)를 숨겨야 한다.

**게다가 DX12만의 사정**: Vulkan의 대응 기능(`vkCmdFillBuffer`)은 버퍼 핸들+오프셋+크기만 받아 이런 이중 핸들 요구가 없다. 즉 이 복잡함은 크로스플랫폼 RHI가 감당해야 할 공통 개념이 아니라 DX12 API 고유의 특이사항이라, RHI 인터페이스에 그대로 반영하면 플랫폼 특이사항이 잘못된 층으로 새어 들어온다.

**대안 — 1-스레드 리셋 컴퓨트 셰이더**: `Dispatch(1,1,1)` + 기존 `SetComputeUAV`만으로 `counter[0] = 0`을 실행하는 셰이더 하나(`ShaderList.cmake`에 한 줄 추가)면 끝난다. 이미 BonePaletteCompute·SSAO·DeferredLighting 등에서 반복적으로 쓰이는 검증된 패턴을 재사용하는 것이라 RHI 확장이 전혀 필요 없고, 새 인터페이스 메서드 하나 추가보다 실질적으로 더 저렴하다.
